# Nimrod

A dedicated cross-platform agent workspace, with bespoke harness integrations. Pi is the primary integration; generic ACP infrastructure is retained internally for future harnesses, without current product UI; Copilot uses its bespoke SDK integration. Preserve bespoke harness semantics and concrete integration boundaries rather than inventing a universal harness protocol. See the [ACP feature reference](.agents/skills/features/references/acp-harnesses.md) for its task-worktree strategy and abandonment checkpoint.

Platform direction: macOS first, Linux next, and possibly Windows later. Nimrod is not a macOS-only product. Design new features—including notifications—with portable behavior and narrow platform-specific native integrations where needed; do not assume macOS APIs or desktop conventions apply everywhere. Windows remains a possible future target, not a current parity commitment. Distinguish intended support from actual per-platform verification.

Read README.md and [.agents/skills/features/references/architecture.md](.agents/skills/features/references/architecture.md) before changes. Preserve exact streaming, tool disclosure, focus and scroll behavior unless deliberately changing the relevant feature contract. Apply the [optimistic interaction policy](.agents/skills/features/references/architecture.md#optimistic-interaction-policy); RPC results are not a general UI gate. Harnesses remain authoritative for conversations, tools, models and configuration.

- For UI discussions or changes, load [nimrod-ui-vocabulary](.agents/skills/nimrod-ui-vocabulary/SKILL.md) and use its shared terminology. Keep agreed vocabulary there rather than duplicating it here.
- For feature implementation/debugging/review, load the shared [features](.agents/skills/features/SKILL.md) skill, then only the relevant per-feature references from its index.
- For release requests, load the dedicated [release](.agents/skills/release/SKILL.md) skill. Present the concrete release preview and wait for subsequent explicit approval before release metadata changes, tags, pushes or publication; ordinary task commit/merge authorization does not bypass this gate.
- **Internal docs** means the agent-facing [features skill](.agents/skills/features/SKILL.md) and its detailed references in `.agents/skills/features/references/` (code map, invariants, storage, platform pitfalls, tests). **External docs** means the user-facing guides in `docs/` (usage, visible behavior, limitations), not publication or deployment outside this repository.
- Document behavior changes in both the canonical internal specification and relevant user guide; implementation-only changes update internal references. Add new items to the features skill index and link new user guides from `docs/README.md` and the main README. Keep developer setup/tooling in `CONTRIBUTING.md`, current specifications in feature references, and superseded investigations in `references/history/`. The verification reference tracks current native evidence and gaps, not every intermediate run.
- Rust is installed and pinned through mise.toml. Use `mise exec -- cargo ...` or `mise run check`.
- Implement directly unless delegation is requested/approved. Completed significant work is pre-authorized for local commits on its task branch and merging into `main`; do not ask for separate commit/merge permission. No pushes without explicit permission.
- Do each new feature, bugfix, refactor, documentation change, or other commit-worthy task on a dedicated branch in a Git worktree under the repository's `.worktrees/` directory (for example, `.worktrees/<task-name>`). Create or reuse the task's worktree before making changes; do not develop directly in the primary checkout or on `main`. After completing significant work, commit the task's changes and merge its branch into `main` as a lightweight local operation, without running builds, tests or checks unless requested. Preserve unrelated changes; if a safe merge is blocked, report the blocker rather than force, reset or discard work. Merging does not authorize cleanup: retain the task branch and worktree unless removal is explicitly requested. Never discard unmerged work or uncommitted changes. When the user requests “cleanup” in the context of merging, it means remove the merged task's worktree with `git worktree remove` and delete its local branch with `git branch -d`. Confirm the branch is merged into `main` and the worktree has no uncommitted changes before removing either; never force removal or branch deletion.
- Keep work local. Tests use fixtures; no paid model requests, live compaction, user-session deletion, or changes to upstream Pi/extensions without explicit authorization.
- Do not alter or reinstall the sibling pi-gui extension when working here.
- Do not use a browser for debugging or development unless the user explicitly asks. Automated tests (including browser-based tests) are fine. Ask the user to validate visual behavior rather than interactively inspecting it.
- Do not run tests, checks or builds unless the user explicitly asks, including during task completion or merge/cleanup. When validation is requested, use `mise run check`; requested validation of scrolling changes also includes `npm run test:browser` (one-time setup: `npx playwright install webkit`), which runs the offline demo in an isolated browser, not the user's app. Build/package the app (`mise run build`, Tauri builds, or equivalent) only on an explicit build request; the user coordinates builds across agents/worktrees to avoid CPU contention. Do not launch or interrupt the user's app/window without approval.
- A user request to **build the app** includes publishing the finished artifact to the primary checkout on `main`, so the installed `nimrod` CLI uses it. Before merge, build the requested task worktree's source with checkout-local targets, then stage and replace the primary checkout's default app artifact (macOS: `src-tauri/target/release/bundle/macos/Nimrod.app`; Linux: `src-tauri/target/release/nimrod`); after merge, build from `main` when requested. Do not merge or change source branches just to publish, redirect worktree Cargo targets into main, or leave only a worktree-local app unless explicitly requested. The user accepts that requested builds can overwrite one another; no additional publication permission is needed. Verify the published artifact/signature where supported. Building does not authorize launching, quitting, or restarting the user's app. See the [build workflow](.agents/skills/features/references/build-cache.md).
- Never replay a prompt after ambiguous delivery. Send clears the draft and applies local UI effects immediately; later results handle errors/reconciliation without changing newer drafts or repeating navigation.
- One directory per window, independently live sessions, an Open sessions sidebar (no tab strip), and command-palette history navigation; see [session usage](docs/sessions.md), [navigation specification](.agents/skills/features/references/session-navigation.md) and [verification status](.agents/skills/features/references/verification.md). Native ownership is window/token-scoped. Resume is user-triggered, never automatic. Pi owns session files; drafts are scoped separately. Stop only owned children; no OS-wide process scans or claims of excluding external writers.
- Do not claim native/platform acceptance from jsdom or unit tests. Document actual verification and remaining limitations.
