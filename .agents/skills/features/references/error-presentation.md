# Error presentation policy

**Status: scoped presentation and routing implemented; remaining producer metadata and native acceptance pending.** This is the canonical policy for Nimrod-owned errors, warnings and delivery uncertainty. Feature references own operation semantics; this reference owns placement, wording, deduplication and lifecycle. OS alerts remain owned by [Notifications](notifications.md).

## Ownership determines placement

Use one window-local notice store and shared renderer, with two ownership-based placements:

- **Session notices** belong only to their originating mounted session. Show them at the top of that session's **conversation area**, immediately above and outside the **transcript pane**, inset by its 20 CSS-pixel gutters. They are in-flow, not overlays or synthetic transcript entries. Send/image/clipboard, connection/startup/restart, explicit Pi notify and model/thinking failures use this placement.
- **Application notice strip** contains only window/application-owned operations: preferences, shared native draft-store health, plugin loading, project operations and notification setup/delivery diagnostics. It remains 48 CSS pixels below the viewport top, below the project/Settings header. Settings, dialogs, welcome, empty-project and pop-out window errors retain this shell placement.
- An open but unselected session records its errors without displaying or announcing them elsewhere. Switching away hides its notices; returning reveals outstanding notices without resolving or dismissing them. No notice-driven sidebar badges/indicators, Issues counter, session switching, sidebar expansion or window focus. Existing harness activity/Unread/input/failure attention is separate, not derived from the notice store. Reporting a session connection notice must not set a sidebar failure flag.
- A session notice must never portal into Settings or an unrelated dialog. A failed model/thinking picker closes its selection interaction through normal focus restoration and reports to its initiating session. Session dialogs that finish before reporting likewise return errors to that session. Generic application palette/Settings failures retain the shell strip.
- Ownership follows the failed operation, not the currently selected session or the catching module. Do not assign application errors to a session accidentally, or flatten session errors into a project/application channel. Truly shared draft-store health remains window-scoped even when detected during a session operation.

The Status area describes agent activity, model/thinking, usage and queues; do not replace it with arbitrary error text. The transcript remains authoritative harness conversation output, including actual agent/provider/tool failures belonging to a turn or tool card. Do not convert that output into a notice or manufacture duplicate application-error turns. Field guidance and non-error progress can remain local; do not add inline/native-validation error bubbles as additional presentations.

## Presentation

Both placements share restrained styling: neutral backgrounds, foreground summary text, a quiet accessible Dismiss control, and optional operation actions. Session notices have a 1 CSS-pixel outline derived from the theme's `--vscode-errorForeground` (60% opacity) and an icon using the same token at full strength. This is one attention treatment for operational notices, not separate warning/error palettes or a cross-harness severity taxonomy; preserve producer severity metadata without reclassifying messages. Application-strip icon styling remains severity-based. Do not use the theme's accent/panel-border color for session outlines or color the whole headline as an error. Session notices do not consume sidebar width or shell layout space.

- Session notices reserve 12 CSS pixels above and below their border, including a persistent gap before the transcript pane. This is outside the scroll container, not transcript padding or a spacer entry. Internal padding is symmetric (8 CSS pixels vertically, 12 horizontally). The first message line, SVG attention icon and SVG Dismiss control share a 24 CSS-pixel alignment height; symbols are geometrically centered rather than dependent on font baselines. Controls stay aligned with the first line when messages wrap or Details expands, never the midpoint of the whole text block. Separate issue rows retain 8 CSS-pixel spacing around their separator.
- A single session issue leads with the actual message in normal foreground color; meaningful operation context is secondary. Omit the known generic `Pi operation` fallback from visible text, announcements and Dismiss labels, without guessing semantics from the message. Application-strip operation/message ordering is unchanged.
- Two or more independent issues collapse to a count summary and an expandable issue list. Adding notices while the list remains multi-issue preserves its disclosure state. The initial collapse must not hide a focused notice control; keep the list open in that case. Returning to one issue shows it directly. Bound each surface to `min(25dvh, 180px)` with its own overflow; notices must not consume an unbounded transcript height.
- Producers may supply separate `details`. Long/multiline legacy messages have a compact first-line preview (160 characters maximum) with the complete original message in Details; preserve both the original message and separately supplied diagnostics when both exist. Never discard diagnostic text or heuristically rewrite/split unstructured Pi messages. This is presentation shortening, not classification of harness text by guessed severity/meaning.
- Unchanged reports retain row/action/disclosure identity. Expanding Details or the list reserves space in the owning layout without overlapping transcript content. Preserve reader intent through the existing transcript resize/follow owner.
- Window notices remain visible/actionable through native HTML dialog top-layer/inert restrictions. The shell node moves into the actual active dialog without changing its viewport location. Only shell notices reserve matching Settings/dialog space; session notices never do.

## Deduplication and lifecycle

- One failure has one visible presentation. Group by owner and operation/cause identity; identical wording alone must not merge unrelated failures. Prefer the actionable outcome over derivative exceptions, e.g. unknown delivery over connection loss from that same cause.
- Independent outstanding issues remain discoverable in their owner's list; later messages must not overwrite unrelated earlier ones. Background ownership is not permission to display a global summary.
- Errors remain until explicitly dismissed, their matching issue resolves, or their owner is disposed. No timed disappearance, automatic retry, or clearing on navigation/unrelated success/routine snapshots.
- Dismissal is presentation only. It does not reconnect, fix an issue, acknowledge delivery, retry a request or remove an operation safety gate. Unchanged repeated reports of that occurrence remain suppressed until resolution or a changed/new failure. Owner disposal clears entries and dismissal bookkeeping.
- Actions require known feature semantics and revalidation at execution. Never replay a prompt after ambiguous acceptance. Detached/closed session owners cannot execute stale actions.
- Announce new/changed visible notices once. Background-session notices do not populate live announcements; selected-session notices announce when revealed. No arrival-driven focus stealing, navigation or transcript scrolling. Dismissal restores a prior control only when focus is vacant, not over another input.

## Wording and submission invariants

Name the failed operation, its effect and an actionable next step when one exists. Session-local notices need not repeat their session title. Window-scoped notices must identify any otherwise ambiguous context. Avoid stack traces/plumbing in primary summaries; keep diagnostics in Details.

Be explicit about not sent versus acceptance unknown. Send clears the composer immediately. Failure/uncertainty never restores an attempted message, alters a newer draft, adds a recovery action or gates a new message beyond normal availability checks. Pi acknowledgement alone establishes acceptance. A later provider failure does not retroactively make an accepted submission not sent; its harness output stays in the transcript. User cancellation is not automatically an error. See [Composer](composer.md).

## Implementation and code map

- `src/application-notices.ts`: NoticeStore retains all window-local issues, causal priorities, independent occurrence IDs, matching resolution and dismissal suppression. `installApplicationNotices` renders only ownerless notices for the shell or an exact session owner for a mounted pane. `setActive` suppresses hidden-session announcements, not storage. The shared renderer owns message-first session presentation, omission of the known generic Pi label, count/diagnostic disclosures, stable unchanged rows and guarded actions. Session attention/Dismiss symbols use fixed SVG geometry; application-strip glyphs and controls are unchanged.
- `src/application-notices.css`: neutral shared styling, gutter-inset session notices with a uniform themed error outline/icon, normal-foreground message headlines, first-line control alignment, symmetric internal padding, a persistent external transcript gap and an additional in-flow grid row only while a session has notices. Shell measured-height reservation remains independent. ResizeObserver schedules pre-paint shell measurement to avoid WebKit resize-delivery loops; session layout is CSS-owned and uses existing transcript viewport observers.
- `src/main.ts`: creates/disposes one notice renderer per mounted session with the shared store; presentation activation coordinates live announcements. Session callbacks preserve ownership and omit redundant session-title prefixes. Connection errors no longer set sidebar failure state. Window preferences/plugin/notification/persistence/project feedback remains shell-scoped.
- `src/command-palette.ts`: session model/thinking selections provide an owned error callback; failure while choosing closes that interaction through normal restoration before reporting locally. Apply failures after an explicit choice still report to the originating session after the picker closes, without closing newer interactions; canceled/stale unaccepted pickers do not report late failures. Generic selections retain shell error routing. No automatic request replay.
- `src/pi/view-host.ts`, `webview-client.ts`: optional presentation-only report/resolve hooks, always supplied by the app. Send/image/clipboard errors route to their session; legacy standalone fixtures retain fallback presentation when no host hook exists. Legacy app submission/tab/storage/preference error nodes remain hidden.
- `src/pi/session.ts`, `reducer.ts`: explicit notify severity uses typed callbacks; process state remains Disconnected rather than diagnostic text. Guard reports by current process token. Harness-authored status/widget text has no generic severity and is not classified by guessing wording.
- `src/settings.ts`, `zoom.ts`, `themes/picker.ts`, `keybinding-editor.ts`, `popout.ts`: application-owned operational feedback uses the shell renderer; progress/guidance remains local. Native dialog actions keep top-layer accessibility and guarded focus restoration.
