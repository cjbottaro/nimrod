# Card plugins

**Status: implemented — automatically discovered/cached personal TypeScript plugins, mounted DOM/capabilities and legacy executable/declarative packages.** User guide: [Card plugins](../../../../docs/card-plugins.md). [Historical extraction](history/card-plugins-declarative.md) records the first implementation; its five-milestone completion applied only to declarative JSON, not the intended outcome.

## Desired outcome and responsibility boundary

- Plugins are authored in TypeScript, shipped as compiled JavaScript plus a JSON manifest. They mount custom HTML/DOM, update incrementally, own local UI state and event handlers, and dispose their resources. JSON declarations may remain a convenience adapter, not the extension ceiling.
- Default tool, reasoning, parallel-tools and requested-edit presentations must exercise the same DOM-capable renderer API as external code, without privileged built-in-only host capabilities.
- Core owns invocation identity, placement, authoritative Pi lifecycle/status, outer disclosure, focus/scroll intent, output caps, renderer selection, capability routing and raw fallback. Plugins own content inside explicit summary/body slots, not the shell or conversation state.
- Rendering is not permission to submit prompts, execute tools or alter harness state. First supported actions are presentation-only: safe Markdown/code rendering, Copy, validated links/files and Pop out. Agent-affecting actions remain a separately designed follow-on.
- One call-ID-keyed shell survives placement/streaming. Manual disclosure and each output reading position survive; generation/execution/result/result-processing phases remain distinct. Local Send clears the editable draft immediately; harness results never clear or restore a newer draft. No upstream Pi/extension changes.
- Portable behavior remains macOS first, Linux next, possible Windows later. Native acceptance is not established by fixtures.

## Built-in tool dogfooding

- Each of Pi's seven built-ins has an independent API-v2 plugin: `read.ts` → `nimrod.read`, `bash.ts` → `nimrod.bash`, `edit.ts` → `nimrod.edit-preview`, `write.ts` → `nimrod.write`, `grep.ts` → `nimrod.grep`, `find.ts` → `nimrod.find`, `ls.ts` → `nimrod.ls`. Bash also matches the existing `shell`/`terminal` aliases. `registry.ts` selects by exported normalized `tools` metadata, independent of argument completeness. Each invocation owns its mounted instance; there is no per-tool shell, transport or privileged capability.
- The pure tool plugins use `tool-shared.ts::toolPlugin`, the existing `presentationPlugin` adapter and public `context.renderPresentation`; edit retains its public-context custom DOM controls. Preserve adapter object identity (including when adding metadata) so existing registered source coverage avoids accumulated DOM text scans. Custom edit DOM still uses core compatibility inspection. Raw recovery, keyed outputs, immutable snapshots, mounted selection, disclosure, focus/scroll and hidden-session catch-up remain core-owned.
- Each tool module owns its presentation callback and preview, with neutral `tool-input.ts` helpers for the unchanged partial-JSON string parser, field/path/search extraction and name normalization. `input-preview.ts` dispatches the same tool-owned preview functions for generic overrides and the parallel-tools overview; it is not the tool-body renderer. Edit no longer delegates to the generic tool renderer.
- Read summaries include valid positive safe-integer requested `offset`/`limit` ranges (default start 1 only when offset is absent); malformed values do not invent ranges. Partial string arguments preserve complete top-level strings only; numeric ranges appear once structured/complete JSON is available. Output remains literal, without parsing fabricated file line numbers or image data.
- Write adds an independently registered `requested-content` literal section for a string `content`, including empty strings, followed by unchanged Pi execution/result sections. This is requested content, never a write-success assertion; errors/interruption do not hide it or Pi output. Existing output caps/reading intent apply to every section. No Markdown/highlighting, control interpretation, async work or new native action is introduced for file/search results.
- `nimrod.tool` remains the generic unknown/custom-tool fallback and explicit override with shared input previews and **literal** output; Bash console formatting now belongs only to `nimrod.bash`. `nimrod.raw` remains preview-free literal output. Dedicated IDs are valid explicit overrides only for compatible tools. Explicit external manifests/personal matches retain precedence over bundled plugins; missing/incompatible overrides still recover to raw rather than selecting another tool plugin.
- Fixtures: `test/builtin-tool-plugins.test.ts` covers seven distinct IDs, aliases/namespace normalization, public personal-export shape (with nonreserved fixture IDs), partial/malformed inputs, preview parity, requested range/content safety, independent instances, phase transitions, append identity/no accumulated DOM reads for pure adapters, retained raw-input identity/disclosure/focus/output positions, precedence and overrides. Console/catalog fixtures target the new Bash ID. `test/browser/builtin-tool-plugins.spec.ts` covers literal write content and independently inspected requested/live/final output viewports. These fixtures have **not been run**; no checks/build/app launch or new native/platform acceptance was performed.

## Multi-harness plugin boundary

**POC source and matching/extraction changes pass offline validation. Native app acceptance pending.** The [ACP integration plan](acp-harnesses.md) owns delivery/acceptance. API v2 gains optional `targets` metadata on executable module exports: `{ backend: 'pi' | 'acp', agent?: string }[]`. Omitted metadata stays Pi-only. Manifest schema remains unchanged; target metadata belongs on the exported module, including legacy manifest-backed modules. Declarative packages stay Pi-only. Exact negotiated ACP `agentInfo.name` supplies optional agent identity; a configured profile label is not that identity.

- Keep one transcript/card runtime for mounting, updates, disposal, immutable snapshots, raw recovery, outer disclosure, output caps and reader/focus intent. Harness/agent-specific plugins interpret native tool arguments/results/lifecycle without impersonating Pi tools.
- Use separate plugin sets: Pi built-ins, generic ACP cards, Copilot SDK cards and optional agent-specific overrides. Unknown ACP agents must work with generic protocol-level presentation; richer cards are an enhancement, not required for basic compatibility.
- `src/card-plugin-targets.ts` validates targets and category selectors. Native ACP `name`, protocol `kind` and human `title` are distinct. `tools` matches normalized names; exported `kinds` matches categories, requiring an ACP target. Either selector qualifies; category-only personal plugins may omit `tools` (legacy manifests still require their original tools schema). Early POC `tools: ['execute']` category matchers migrate to `kinds`/`defineKindPlugin`; Pi matching is unchanged.
- Automatic ACP external candidates rank exact-agent before generic-ACP targets, then name before category-only matches, then existing catalog order. Optional synchronous `matches` evaluates an immutable snapshot at selection; false/throw skips that candidate. `catalog.ts::callbacksAllowed` checks current executable enablement/trust (or personal autoload/discovered membership) before applicability and again before `supports`. Asynchronous reloads may retain old catalog entries, but cannot authorize their callbacks using old settings. Pi automatic selection keeps catalog order, with the same optional applicability hook; explicit Pi overrides remain pinned and bypass candidate search. After mounting, `supports` still means compatibility and failure latches to raw recovery, not reselection. Late metadata/arguments never reshuffle mounted renderers. Pi's tool-only overrides never apply to ACP. Copilot SDK now uses explicit `copilot-sdk` targets, never automatic ACP aliasing; its fixtures remain unrun.
- These are public card-content plugins, not harness controllers or app-wide UI plugins. The internal [harness presentation boundary](harness-presentation.md) supplies interaction policies, controls, status and session actions; card plugins have no new execution capabilities.
- Share optional visual building blocks, not a universal tool-execution schema. Pi Bash and Copilot shell adapters may use the same command/output component while retaining separate payload parsing. A parsing fix belongs to its adapter; a visual-component or engine fix benefits all consumers.
- **Public-component dogfooding is required:** bundled and external plugins use the same supported runtime component API/import surface, lifecycle hooks and presentation capabilities. No private built-in-only shell/output renderer. Components accept small presentation-oriented inputs (command text, output, supplied exit status/state), never require Pi-shaped records, and are optional for custom DOM authors.
- Public does not mean unrestricted transcript internals. Core still owns shell identity/status, disclosure and scroll; supported hooks route layout changes and cleanup. Preserve existing trust boundaries, lifecycle cancellation and raw fallback.
- `src/card-plugin-api.ts` remains the standalone type contract. `src/card-plugin-ui.ts` is the optional public browser runtime (local checkout imports, not a published npm package): `definePresentationPlugin`, `defineToolPlugin`, `defineKindPlugin`, `rawToolPresentation`, `shellPresentation` and argument/preview helpers. Pi Bash, the optional Copilot shell adapter and `examples/card-plugins/acp-shell/plugin.ts` use this same surface. The existing native bundler resolves local runtime imports and fingerprints their contents through its dependency graph; API changes also invalidate the SDK contract hash. No new package alias/resolver is assumed.
- `dom-card-renderer.ts` delegates its compatibility pure-presentation adapter to the public factory, preserving bundled object identity/source-coverage optimization. Separately bundled helper copies conservatively use normal external raw inspection; no extra host capability is reserved for built-ins. `ToolCardData` adds `source`, `title`, `kind` and retained `native` metadata without changing Pi's existing fields. `toolMessageBlock` carries these optional ACP fields to the shared controller.
- `test/acp-cards.test.ts` bundles/imports the external shell example, mounts it through the real controller and tests Pi/ACP/agent scoping, raw recovery and public-only imports for shell entries. Extended name/category/applicability and mixed-harness regressions pass in the full offline gates. See [current evidence](verification.md#current-automated-validation). Broader migration of all bundled non-shell tools to public-only imports remains follow-on; the POC dogfoods the shared shell component end-to-end in source.

The revocation-order follow-up adds `test/card-plugin-callback-guards.test.ts`: suspended reload reads/imports verify that revoked trust, disabled manifests, disabled personal autoload and removed personal entries cannot execute `matches` or retained `supports`. These new fixtures have not been run; earlier full-gate evidence is recorded in [verification](verification.md#current-automated-validation).

Filesystem work runs on a blocking worker; compiler processes are owned and killed/reaped on timeout. `cards.autoLoad: false` is the native escape hatch (validated natively and in the frontend).
- CLI compilation uses fixed browser ESM/ES2022 options and disables implicit tsconfig discovery (`--tsconfig-raw={}`). Static local imports and already-installed browser packages are supported; Node builtins, static external runtime imports and extra CSS/asset outputs are rejected. No type-checking or package lifecycle code executes. Maximum output 1 MiB, input file 8 MiB, cache record 4 MiB, 4096 inputs, 100,000 resolution-tree entries, 20s per compiler attempt; limits fail visibly rather than truncate code.
- Warm loads validate entry/import content hashes, module resolution directory/file inventories, package JSON/lockfiles, compiler binary hash, fixed options and embedded SDK contract hash. Only actual input contents and resolution metadata are hashed—not all dependency file contents. Conservative metadata changes may rebuild. Cache hits spawn no compiler; imports are still evaluated later in the webview.
- A changed resolved graph is retried against a fresh before/after snapshot (up to three passes); missing prior inputs do not pin an obsolete graph. User files are not locked, so this does not exclude arbitrary external writers. Stale/corrupt cache or changed code rebuilds; failed edits never fall back to an old bundle. Atomic private cache records serialize across windows via the shared compiler gate.
- Native fixture tests run real esbuild only on disposable sources: cold/warm across managers, zero warm compiler runs, source/dependency edits, added/removed resolution candidates, package/lockfile changes, cache corruption/identity, browser-only/error behavior and shared publication. No user's source/config/cache, model or app is used. Stage E `mise run test` passes **494 TS/Node tests** and **122 Rust tests** (two opt-in smokes ignored), docs/formatting/Clippy. No UI/scroll changes in this backend stage; browser tests resume with stage F. No app package/build/launch or native sidecar acceptance.

### Automatic catalog and reload (stage F)

- `CardPlugin.tools` supplies metadata for personal sources (optional for manifest packages). `personalRenderer` validates version/ID/tool matching/functions after trusted module evaluation. Code-based metadata requires evaluation; duplicate source IDs may already have module-global effects before rejection.
- `catalog.ts` keeps explicit manifest precedence, then sorted native personal entry order, then bundled fallback. Personal entries need no per-file settings/trust; `cards.autoLoad` defaults true. Disabling it immediately blocks managed personal actions/updates, and no discovery/compilation is requested. Deletion/removal becomes authoritative on explicit reload/startup, not a file watcher.
- `card-plugin-loading.ts` coalesces same-signature requests, guards stale/disposed reporting and permits forced source-only reloads. `main.ts` starts it without awaiting it before shell/session boot. Until completion new cards may use bundled renderers; mounted selection stays fixed afterward. Source loading/errors never connect/restart Pi, navigate, submit prompts or clear drafts.
- Settings shows loading/completed/cache-hit status and errors. `reload-card-plugins` is a registered project action with an empty default binding and palette command using the same function. Override/unbind/modality/default-hint regressions are covered. Reload refreshes only the catalog for new cards, preserving inspected DOM/disclosure/local state/focus/reading intent.
- The application-scoped compiler's cancellation/gate are shared across windows; app Quit cancels and observes its owned helper exit concurrently with owned Pi shutdown. Closing one window does not interrupt other windows' shared compiler work. No process scans, Node backend or user-session mutations.
- Tests: `personal-card-plugins.test.ts` covers source metadata/no manifest/trust lists, disable/removal, precedence/duplicates/errors, stale loads and coalescing. Shell fixtures prove boot/drafts during delayed compilation and bind/unbind reload without Pi restart. Browser personal-plugin fixtures execute compiled example ESM under CSP, simulate the native cache boundary, verify reload/new-card edits/inspected state and delayed-startup/disable behavior; real on-disk compiler invalidation is separately exercised by native fixtures.

## Execution decision

The initial executable API is **explicitly trusted, in-process JavaScript** to allow direct incremental DOM rendering through the same API as bundled plugins. It is **not a sandbox**: in-process code can reach webview globals; host capabilities and controlled slots are supported API boundaries, not security confinement. Personal TS/TSX entries are trusted by placement in the dedicated config-adjacent user directory. Existing manifest packages still require explicit per-package trust before entry code loads; JSON declarations require no executable trust. No project discovery, remote package fetch or arbitrary/user module execution during tests.

Isolated untrusted-code loading is a separate future architecture; do not describe exception containment as protection from malicious code, hangs, global listeners or arbitrary IPC. No paid providers, live sessions, user config mutation or interactive browser inspection during implementation.

## DOM contract (milestone B)

- Standalone `src/card-plugin-api.ts` defines API v2 (internal `DomCardRenderer` alias): `mount(context)` returns `update(data, state)` / `dispose`. Context exposes the owner document, plugin-owned summary/body slots, abort signal, managed `on`, pre/post-change `mutate`, safe Markdown and explicit keyed output registration. This is trusted DOM access, not confinement.
- `DomCardController` supplies detached/deep-frozen data snapshots and frozen lifecycle state, so supported renderer callbacks cannot mutate retained core data. `immutable-snapshot.ts` shares immutable primitive strings and only its own branded deeply frozen JSON subtrees (not arbitrary caller-frozen roots); authoritative tool arguments are snapshotted once and reused across output updates. Non-JSON compatibility values remain detached. API v2 still supplies full card snapshots; no new streaming API or bundled-only callback was added. It owns exactly-once instance/resource cleanup, card-local failure latching and raw fallback. It removes managed listeners on mount/update/event/rejected-event failure and disposal; late managed callbacks become inert. Arbitrary unmanaged events/timers and module-global exceptions remain plugin author/trust responsibilities.
- Pure built-in tool, generic fallback and declaration renderers use the public `presentationPlugin` DOM adapter; edit, reasoning and parallel plugins directly mount/update their DOM through the same context. Legacy pure presentation types are internal adapter helpers, not the executable API. No bundled-only DOM or host privileges.
- Hidden session views retain mounted instances but defer renderer-driven mount/update/removal reconciliation until a synchronous latest-snapshot catch-up on reveal. Intermediate presentation updates are not replayed; Pi state/event processing remains ordered and live. Reset/disposal still releases instances immediately. This does not suspend arbitrary plugin-owned timers/async mutations; see [transcript interaction](transcript-interaction.md).
- Core retains summary/status/disclosure and raw inputs. Custom tool DOM that does not include the retained execution/result sections gets an independent closed Raw output disclosure outside its slots. This includes helper-rendered sections overwritten during the same or a later synchronous `update`. Only internally identified pure presentation adapters and core fallback may skip DOM-text inspection using the existing registered-output/content cache; arbitrary mounted plugins retain actual-content inspection, even if they use `renderPresentation`. Synchronous failures retain latest raw content without rebuilding healthy siblings.
- Shared presentation sections support opt-in `format: 'console'` for ANSI/log progress rendering; source remains exact in independent raw recovery when transformed. The [transcript cards specification](transcript-cards.md#console-style-command-output) owns controls, cumulative-snapshot handling and limits. This is shared by bundled command cards and plugins, not a private rendering path.
- Registered output viewports get host lifecycle caps and per-key reading-position preservation, including terminal transition. `mutate` captures follow intent/output inspection before asynchronous content changes; after-change routing uses the existing `TranscriptScroll` owner. Plugins must use it for later layout mutations; direct DOM mutation alone cannot promise scroll preservation.
- Existing direct-child geometry is preserved by a display-contents summary slot and tool-body section selectors. View removal/reset/disposal still owns cleanup. No executable loader or host actions shipped in B.
- `test/dom-card-renderer.test.ts` covers custom mounted input/focus/local state, multiple output viewports, mount/update/managed event failures, rejected callbacks, raw recovery and disposal. Lifecycle/mutation callbacks must be synchronous; rejected async lifecycle promises are consumed and fail to raw recovery. Validation: `mise run test` passes **480 TS/Node tests**, **114 Rust tests** (two opt-in smokes ignored), docs/formatting/Clippy; offline WebKit **66 tests** pass. No app build/launch or new native acceptance.

## Presentation capabilities and interactive proof (milestone C)

- Context offers safe `markdown`/`code` rendering, `copy`, `openLink`, `popOutCode`, and capability availability flags. Calls validate bounds/links and require a connected plugin body, active view and no modal; detached/removed/disposed managed controls do not deliver actions. There is no prompt/tool/config/transport API.
- `main.ts` injects native clipboard, project-owned validated links and existing session-pop-out routing. Presentation actions remain available for historical/disconnected cards; they do not connect Pi or require a child token. `open_card_link` derives cwd from the native window's registered project and reuses existing link/editor validation. Pending pop-out requests retain existing selected-session guard/serialization.
- `editDomRenderer` mounts compact change-count/Wrap/Copy toolbars through the public context. Filename-first summaries retain a muted, left-truncated directory and full-path accessibility/raw inputs. Input-backed line diffs retain unchanged context, with `1 of N` only for multiple valid substitutions; no applied-file claim or invented file line numbers. `edit-diff.ts` strips common prefix/suffix, then matches the middle with a bounded LCS (250,000 cells); larger middles fall back to literal removal/addition without truncating content. Per-index old/new caching avoids repeating diff work on lifecycle-only updates.
- The public `CardPresentation.rawInputsPlacement` (`before` default / `after`) lets the host move its retained raw disclosure below the body without plugin shell access. Edit previews request `after`. Routine completed raw sections are omitted from the primary body, causing core's existing collapsed Raw output recovery; running/error/stopped sections remain prominent. Malformed/partial inputs keep the generic presentation. Existing raw disclosure, controls/focus, keyed output inspection, outer disclosure and lifecycle policy remain mounted/authoritative.
- Copy copies the current input-backed diff (context included); Wrap changes only its local visual whitespace through managed mutation. Expected clipboard failures remain inline, stale control/completion handlers are ignored, and focused controls use aria-busy rather than disable during Copy. Neither action invokes Pi or claims an applied-file diff.
- Existing safe-code Copy uses injected presentation clipboard when available and retains the correlated fixture fallback otherwise; read-only Markdown links similarly use the project presentation bridge. Core sanitized content never navigates the app webview.
- Tests: `card-plugin-actions.test.ts` covers capabilities, bounds/unsafe links, historical data, active/modal/disposed guards, exact requested diff, focus and late completion. Native-view fixture tests exercise disconnected history and modal delivery suppression. Browser `card-plugin-actions.spec.ts` runs an offline synthetic edit and records clipboard IPC only; no real clipboard, provider, file edit or app is touched. The Copy control uses pending/aria-busy rather than disabling a focused button, preserving native keyboard focus.
- Validation: `mise run test` passes **484 TS/Node tests**, **114 Rust tests** (two ignored opt-in smokes), docs/formatting/Clippy; **67 offline WebKit tests** pass. An existing single-instance lock fixture failed once, passed in isolation and on subsequent full gates; no unrelated instance code was changed. ## Trusted executable loading (milestone D)

- `src/card-plugin-api.ts` is the canonical standalone type-only SDK; internal controllers re-export/use its types rather than publishing dependencies on app implementation. `examples/card-plugins/command-summary/` supplies a versioned manifest and TypeScript source included in normal `tsc` checks and compiled only in-memory by fixtures. [Authoring guide](../../../../docs/card-plugin-api.md) owns public usage; compilation tooling is in Contributing.
- `executable.ts` validates strict API-v2 manifests (ID, normalized tool matches, local `.js`/`.mjs` entry) and default-export identity/version/function shape. `importCardModule` evaluates a self-contained browser ESM blob, revokes the URL and times out pending module imports after 5s. It cannot interrupt blocked JavaScript or undo globals/late top-level effects. No eval, runtime TS compiler, npm resolver or remote loader.
- Legacy `cards.plugins` enables manifests; `cards.trustedPlugins` independently grants per-filename executable trust. V1 declarations use no code trust. Frontend/native validators reject duplicate/path/URL/bad-shaped trust entries. Backend module reads require both current enablement and trust, compare the manifest snapshot and validate the JS entry before bounded reads. Manifest limit is 256 KiB; module limit is 1 MiB. Regular non-symlink files only; Unix opens use no-follow/nonblocking flags. Windows race/native behavior remains unverified.
- `catalog.ts` rejects duplicate IDs before evaluating later entries, checks generation before starting module evaluation and before publishing results, and invalidates pending loads on window disposal. Already-started trusted imports cannot be undone by generation changes. Package/source edits are not watched continuously; explicit Reload card plugins/configuration reload/window reopen rescans them under the applicable personal-directory or legacy per-file trust.
- New cards use the current catalog; mounted renderer selection stays fixed. Current enablement/trust is consulted for each managed callback/action/update, so revocation/removal disposes the affected instance to raw fallback before new managed side effects. It cannot cancel unmanaged/global effects or already accepted native operations; window teardown is required to fully retire code.
- Production/dev CSP permit `blob:` script modules without adding unsafe-eval or remote script/connect origins. The blob is native-read, explicitly trusted code—not a sandbox. There is no package stylesheet/resource loader; local styles inside owned slots are a convention, not isolation. External matching is currently tool-only; bundled reasoning/parallel still use the same context.
- Tests: `executable-card-plugins.test.ts` covers manifest/export mismatch, trust-before-read/evaluation, duplicate/stale/disposed loads, public example compilation/custom DOM/local state/Copy, revocation, latest historical raw recovery and update failure/disposal. Native fixtures cover trust/manifest/entry/bounds/symlink checks. Data-mutation and already-started import tests distinguish immutable supported snapshots and stale publication from sandbox claims. Browser `typescript-card-plugins.spec.ts` executes real fixture ESM under production-shaped CSP, verifies streaming identity/focus and Copy, trust opt-in/revocation and incompatible module errors. These are not native Tauri loading/permission acceptance.

## Material constraints

- Pi tool results are flattened to text; structured/non-text result metadata is not currently preserved. The requested-edit proof uses actual structured input substitutions and must not claim an applied-file diff. Rich custom Pi content remains separate transport/history work.

- Arbitrary plugin event/async exceptions require managed callbacks and disposal guards; no synchronous controller can catch arbitrary outside callbacks or halt infinite loops. Document these trust boundaries.
- Continuous hot reload, plugin install/selection UI, external reasoning/parallel matching, executable sandboxing, app-wide extensions, stylesheet/resource loading and agent-execution actions remain follow-ons. Slot-local styles are allowed by convention, not confined.
