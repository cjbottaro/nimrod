# Window translucency

**Status: independent macOS blur implemented; native enable-flash reproduced in an isolated AppKit/WKWebView probe; no flicker fix or full native acceptance.** User guide: [Translucency](../../../../docs/translucency.md). Related: [Themes](themes.md), [Preferences](preferences.md), [Settings layout](settings-layout.md), [Verification](verification.md).

## Contract and schema

Global-only paint preferences, separate from color-theme selection:

| JSONC key | Values | Default |
| --- | --- | --- |
| `appearance.backgroundOpacity` | integer 0–100 | 100 (opaque) |
| `appearance.backgroundBlur` | integer 0–40 (0 = off) | 20, or 0 when legacy frosting is false |

TypeScript and Rust validate both numeric settings. Explicit nulls are invalid. The legacy global-only `appearance.frostedBackground` boolean remains validated: when the numeric blur key is absent, false maps to 0 and true/absent maps to 20. An explicit numeric value wins; no automatic migration or file rewrite. Project files reject these keys as global-only. Existing comment-preserving queued/CAS preference writes and revision-ordered broadcasts own persistence. Original theme palette tokens and surface-density recipes remain unchanged. At opacity 100, effective native blur is 0 while its saved strength is retained. Native macOS title bars deliberately follow the theme.

Translucency always covers the entire window: Project bar, Session sidebar, conversation, Settings and pop-outs. There is no area selector or sidebar-only rendering path. `WindowAppearance` and its save/preview plumbing contain only opacity and blur. The removed global `appearance.translucencyArea` key is ignored like any unknown setting, including stale values; preserve it and its comments without migration or automatic rewrites. Old `chrome` values must not keep any surface opaque. Performance reports retain a constant `area: window` and effective `window`/`off` state for their existing report shape, not a configurable surface choice.

Global Settings exposes independent opacity and blur sliders. Blur appears only with runtime native blur support; the compatibility capability field is still named `frost`. Project settings hides the entire control group while following global appearance. Their accent-filled tracks initialize from saved values before interaction and follow programmatic reloads through the [shared range-input presentation](settings-layout.md#range-inputs); this adds no preview or persistence events. Both sliders' `input` previews Settings immediately and broadcasts paint-only values to project/reference windows; `change` commits once. Pending per-field previews survive older broadcasts/save completions; a failure discards only its matching local edit, never a newer one. No automatic save retry, window recreation, harness calls or navigation. At opacity 0 and blur 0 the base is clear/sharp; at opacity 50 and blur 0 it is sharply theme-tinted; increasing blur softens the backdrop without adding material tint. Existing panel/control readability floors remain.

Code, suggestions and user-turn backgrounds retain solid backing surfaces. Ordinary dialogs share a denser glass shell when translucency is effective; opaque mode retains solid dialogs. Role-derived interaction/panel overlays keep the Status area and notices denser than the conversation while changing continuously with the slider. Application notices paint a corresponding denser single strip surface because they have no tinted parent; their separate banner rows remain transparent over that strip. Session notice wrappers are transparent and each individual banner consumes the denser notice overlay token, preserving separation without stacking the same tint twice. Shared primary/secondary/hover/selected/danger button fills follow the same endpoint-continuous policy throughout the window. Filled primary/secondary/danger controls keep a stable opaque foreground, and derive sufficient fill density for contrast through the shared [filled-control policy](#filled-control-contrast). Do not interpolate opposite foreground colors. Text/icon opacity, notice error borders/icons, focus rings and interaction geometry remain unchanged; disabled controls retain their existing dimming.

The full-window Settings dialog/backdrop is transparent while translucency is effective; underlying Project bar/workspace are `visibility:hidden` only while that Settings dialog is open, retaining layout, scroll geometry and mounted controllers. Each Settings surface paints its own tint exactly once; the modal must expose the native backing, not the conversation under it. Ordinary dialogs use the shared modal surface described below; their modality/focus/scroll contracts are unchanged.

## Visual hierarchy across the opacity range

**Invariant: preserve the same visual hierarchy throughout the slider's range.** Translucency changes surface density progressively, not the identity of surfaces. Status area/session notices must remain distinguishable panels below 100%, rather than collapsing into the conversation's background. Buttons and their hover/selected states keep their emphasis ordering. Crossing 100 → 99 must not switch to a visibly different low-density recipe.

- Base content follows the slider directly. Interaction overlays are lighter than Status-area/notice overlays; a panel composited over a base must remain denser than that base at every value below 100. At 100, all fills are opaque and palette color contrast preserves the hierarchy instead of alpha differences.
- Visible composited surface densities are continuous and monotonic (contextual button overlay alpha may ease down as its parent gains tint), converge to alpha 1 at the opaque endpoint, and reproduce the opaque presentation there (original palette pairs where readable; repaired filled-control pairs otherwise). Do not use fixed low button fills or `opacity × 0.2` panels for every value below 100: those create an endpoint discontinuity. Do not multiply the container's opacity, fade text, or reintroduce an 85%-opaque overlay over an already tinted base.
- `windowSurfaceOpacities` owns the current calibration: normalized slider `p = opacity / 100`, endpoint easing `e = p^8`, overlay role `a = minimum + (1 − minimum) × e`. Baseline low-end minima: interaction/secondary 0.10, Status-area/notice panels 0.25, primary 0.35, primary hover/selection/danger 0.45, secondary/toolbar hover 0.30. Filled-button minima are additionally raised by the contrast policy below; these baseline curves are not a contrast guarantee. These floors retain hierarchy at a clear base; easing keeps intermediate settings modest while smoothly approaching the original opaque palette. At 65%, interaction/panel overlays are about 12.87% / 27.39%, giving a session notice ~74.6% effective alpha over the 65% base, not the base's same transparency. Status composes over the interaction area as well.
- A parent/base with alpha `p` plus overlay `a` has effective alpha `p + (1 − p) × a`. The fixed-position application strip uses this effective notice alpha as its own single fill. Never apply the base tint again at each nesting level. Preserve every consumer's original palette recipe (including distinct primary/danger foregrounds, secondary/control hover, list/quick-input/suggestion selection fallbacks).
- Native compositor blur remains separate from the CSS theme tint; neither changing its strength nor selecting a theme changes the CSS hierarchy calibration. Code and suggestions remain explicit solid-backing exceptions. Ordinary modal panels have their own denser whole-window glass role. Reduce Transparency restores opaque fallbacks without changing saved preferences.
- Acceptance: inspect 100, 99, 95, 85, 65, 50, 25 and 0 with both dark/light palettes. Panels must not disappear just below 100; lowering opacity preserves their ordering and recognizable treatment. Native desktop/material contrast still needs user acceptance; DOM/math fixtures establish the implemented curves, not native visual quality.

## Shared modal glass

In whole-window mode, `windowSurfaceOpacities` adds a modal tint floor of .72, eased to 1 with `p^8`. The black scrim eases from .20 to the original 1/3 alpha at the opaque endpoint; theme-preview palettes retain their existing transparent backdrop exception. `modal.css` remains the sole shell authority and consumes the shared `--nimrod-surface-modal`/backdrop values. Command palette, all session pickers, deletion review, host dialogs, recorder and Pi's editor overlay inherit the same treatment—not separate per-dialog styles. Native modality, stacking, keyboard handling, layout, focus restoration and scroll ownership do not change.

Scoped `--modal-field-surface`/`--modal-inset-surface` roles keep inputs and deletion-tree panels from filling the glass shell with opaque rectangles. They use the existing interaction alpha over the modal, not another window tint. Text/icon opacity remains 1; borders and shadows preserve separation. Opaque, unsupported-platform and reduced-transparency modes restore solid original surfaces/scrims. No CSS blur/filter or native material changes are introduced; the app beneath can show through the dialog.

## Filled-control contrast

`src/button-surfaces.ts` owns palette-independent pairing for primary, secondary and danger buttons (including hover). Preserve the supplied text colour if it has at least 4.5:1 contrast against the solid fill; otherwise use a readable neutral. Button-specific colour roles are opaque RGB, even if the source palette supplies alpha. Never rewrite `--vscode-*` tokens or branch on theme IDs. Incompatible hover hues use the normal hue and stronger hover density so the same text remains readable. Secondary control hover retains its normal hue rather than interpolating unrelated fill colours.

Calculate a minimum fill alpha sufficient for that text over **any** sRGB underlay: use the composited black/white luminance interval; if the foreground falls inside it, an intermediate underlay can give contrast 1. Binary-search the safe alpha, then use `max(contrastMinimum, roleMinimum + (1 - roleMinimum) × p^8)`. The contrast minimum is a **lower bound**, not the base of another opacity ramp. Easing upward from it stacked extra density and made buttons nearly solid around 90%. Hover density is never below its normal state. This preserves continuous/monotonic composited density and avoids mixed, low-contrast label colours. Some buttons necessarily stay denser at low window opacity; do not reduce the floor just to match another role's numerical alpha. Existing panel/interaction curves are unchanged. Valid solid opaque pairs keep their colours; originally unreadable/alpha button pairs are repaired at the opaque endpoint too. Disabled-control dimming remains intentional. Transparent toolbar icons and ordinary text retain their existing treatment; this is a filled-control contrast policy, not native accessibility certification.

Known tinted parents now contribute a conservative channel-wise contrast credit: sidebar uses the widget tint, Project/Settings header uses the editor tint, and ordinary modals use their actual modal tint. For dark text, credit is the minimum parent/fill channel ratio; for light text use distances from white. Include the parent palette's alpha. Discount the contrast-protected overlay `a` to `(a - p*k)/(1 - p*k)` and take the maximum with the original eased role curve. The arbitrary five-point discount cap is removed: only the contrast and visual-role lower bounds determine density. This can lower overlay alpha slightly while the total `p + (1-p)*a` remains monotonic. Foregrounds and the 4.5:1 target remain unchanged; root/unknown parents receive no credit. All palette types use the same policy.

The controller caches credit coefficients at palette application and publishes context-specific density tokens on paint. CSS re-declares the semantic fills at those known parents so variables resolve locally rather than inheriting an already-computed root fill. Slider updates require no ancestor inspection or additional computed-style reads.

Recompute palette roles only at installation, explicit completed theme publication or inherited-system scheme changes. The applied-theme snapshot includes a palette signature, so changed button colours with the same ID/background also invalidate presentation. Slider ticks only update density; unchanged state broadcasts do no palette/style reads.

## Theme-led buttons

New session and Send/Stop consume the same theme-derived primary roles as other primary buttons. Keep the shared .35 normal / .45 hover role minima, palette-derived contrast floors and known-parent credit described above. Do not override these two controls with lighter fill minima, sheen, edge lighting or opacity-dependent corner geometry. Button and selection colours may intentionally coincide or differ according to the theme; preserve those palette relationships rather than sourcing button colours from an unrelated accent/selection role.

The lighter-button trial was withdrawn: its .18 / .32 minima could leave Nimrod's contrast-limited fill unchanged while weakening Tokyo Night's button surface. The shared baseline restores theme-led treatment without changing 100% opacity, Reduce Transparency, whole-window scope, native blur, focus/disabled behavior or hit targets. Updated controller/browser fixtures cover shared density roles for Nimrod/Tokyo Night and unchanged geometry/opaque reset; they are authored but unrun, and packaged visual review remains pending.

## Live appearance preview

The native `SettingsWindow` owns one ephemeral, generation-authorized, revisioned `{revision, opacity, blur}` snapshot. Only its current frontend may call `preview_window_appearance`; all window types subscribe to `nimrod-window-appearance-preview` and read `window_appearance_preview_snapshot` through `native-window-appearance.ts`. Opacity is bounded 0–100 and blur 0–40; each can independently be null to clear. Subscribe before fetching the initial snapshot; reject stale replies/events. Newly opened project/reference windows read the current preview. This state is not JSONC, a theme preview, a project override or a harness event.

The frontend coalesces unsent slider values through one serialized latest-value publisher, while painting Settings locally immediately. Commit success/failure clears only its matching edit; older completions cannot cancel a newer drag. Native Settings destruction clears the preview and rejects late old-generation commands, including when unload IPC cannot run. An uncommitted close restores saved opacity and blur; clearing one field must not cancel the other's active preview. File writes still use the existing preference writer once on `change`; no per-input persistence, focus/navigation, window recreation or session work.

## Native title bars and first presentation

macOS uses native **Transparent** title-bar style, not Overlay or custom HTML chrome. Keep the title, traffic lights, window drag/resize, native menus/cycling and the separate 48 CSS-pixel Project/Settings header. The native title-bar tint follows that window's editor-background/Project-bar colour and effective background opacity (opaque under Reduce Transparency), including same-dark/light-mode theme previews and restoration. Caption/text appearance follows the explicit theme mode even when blur is off; Nimrod (system) keeps inherited native appearance.

`titlebarTint` converts the allowlisted 3/4/6/8-digit hex colour to bounded sRGB RGBA bytes. The single typed frontend appearance pipeline serializes/coalesces blur/theme then title tint, and skips unchanged colour/opacity/theme-identity requests. Native apply receives `updateTheme`: initial application or a changed dark/light/inherited identity reapplies native appearance; blur-only updates do not. Only a theme change invalidates title tint, whose cache identity deliberately excludes blur radius. Thus slider ticks cannot rebuild native appearance/title layout or retry an unchanged failed title tint. Theme identity remains in the tint cache so older same-colour work cannot suppress retinting a changed title view. Slider and same-mode palette changes do not reinstall blur. Successful tint is refreshed on native activation; failures remain separately owned/deduplicated and are not silently retried on state broadcasts. The explicit `applyTheme` snapshot detects same-mode palette changes. No root-style observer or presentation inference from DOM mutations is used.

`window_appearance.rs` dispatches `tint_window_titlebar` only against its invoking window on the main thread; AppKit implementation is isolated in `macos_window_appearance.rs`. Prepare native layout, use the standard Close button's public NSView ancestry, and tint only a full-width, title-height (≤120pt) existing view layer. Do not change the NSWindow's nearly clear backing to a solid theme colour—that would destroy content transparency. No inserted hit-test view, moved controls, title hiding, full-window overlay or geometry mutation. Bounded unsupported/full-screen hierarchies retain transparent native chrome; their precise native tint/resize/full-screen behavior needs acceptance. Linux/possible Windows title decorations are not changed.

Cold **global Settings** exposes `ready`/`settled` and remains natively hidden until the mounted palette/appearance/title-tint/zoom state is prepared. Initial effect failures settle to the error/fallback presentation, not a permanently hidden window. [Settings layout](settings-layout.md#first-native-presentation) owns the generation-scoped, idempotent reveal and its narrow optimistic-policy exception. Project and reference-window startup are not newly gated.

## Native boundary and platform scope

- `src-tauri/src/window_appearance.rs::prepare` is composed by `window_presentation.rs::prepare`, alongside—but separate from—the navigation guard; all welcome/project/Settings/pop-out constructors pass it. macOS/Linux backings are transparent from creation, but opaque CSS remains the initial/default state. No runtime window replacement, geometry mutation or focus action.
- Native commands report `{platform, transparency, frost, reducedTransparency}` and apply only to the invoking `WebviewWindow`, never a frontend-provided label. No process/session privileges or OS/compositor configuration.
- macOS uses private WindowServer `CGSSetWindowBackgroundBlurRadius` with `CGSMainConnectionID`, runtime-resolved via `dlopen`/`dlsym` from SkyLight and cached for process lifetime. The native recipe also requires `SLSDisableUpdate`/`SLSReenableUpdate`; missing either reports no blur capability instead of exposing an unbatched fallback. No `NSVisualEffectView`, Popover material, private layer-tree manipulation, screen capture or pixel access. CSS owns all theme tint. Native apply receives bounded `blur: 0–40`, `dark: boolean | null` and `updateTheme: boolean`; radius 0 explicitly removes blur. Missing symbols report no blur capability and retain plain transparency; a nonzero native return attempts removal and reports an application notice, without substituting a dense material or retrying identical failed requests. This is a private-API/direct-distribution dependency, not a public macOS compatibility or Mac App Store guarantee. The same primitive is used by [Ghostty](https://github.com/ghostty-org/ghostty/blob/main/src/apprt/embedded.zig), [kitty](https://github.com/kovidgoyal/kitty/blob/master/glfw/cocoa_window.m) and [winit](https://github.com/rust-windowing/winit/blob/v0.30.13/src/platform_impl/macos/window_delegate.rs). Resolve/use the invoking NSWindow on the main thread; keep it non-opaque with a nearly clear backing (see below). Keep **window-local** `NSWindow.setAppearance`, never Tauri/Tao `set_theme` (which leaks to NSApplication); explicit modes apply just to that window and null leaves Nimrod (system) inherited.
- macOS backing uses black alpha **0.0001** (0.01%) rather than exact `clearColor`. Fully clear titled windows can use content-derived shadows, leaving rectangular/stale artifacts with background blur. The epsilon-alpha workaround is prior art in [Ghostty's native window](https://github.com/ghostty-org/ghostty/blob/main/macos/Sources/Features/Terminal/Window%20Styles/TerminalWindow.swift) (0.001) and [Zed's shadow investigation](https://github.com/zed-industries/zed/pull/27403) (0.0001). Initialize only when the native backing is opaque/zero-alpha (AppKit's typed getter is non-null) and invalidate its shadow once; do not reset backing/shadow per radius tick. This does not fade content, set a solid theme backing, disable native shadows, add an overlay, set a hardcoded corner radius, or change native frame geometry. AppKit still owns rounded corners. The user subsequently confirmed that rounded corners now look correct, but 0→nonzero blur still flickers. This is limited corner acceptance, not full native acceptance.
- Native radius setters (including best-effort removal on setter failure) are enclosed in one synchronous **connection-scoped WindowServer update batch**. Only the invoking window's radius is changed; batching briefly defers presentation for Nimrod's own main connection, not an external connection. `SLSDisableUpdate` must succeed before any setter runs. An RAII guard attempts `SLSReenableUpdate` exactly once on normal success, setter failure or Rust unwind; a normal-path resume failure is reported, not silently ignored. No sleeps, async work, WebKit drawing, screen capture, global debug flags, window hiding/reordering or run-loop turn inside the batch. Zero remains a real radius 0, never a warm-up radius. This batching remains implemented, but the isolated macOS 27.0.1 probe reproduces the 0→nonzero grey flash with and without it; it is not an effective transition fix on that host. See [Native enable-flash investigation](#native-enable-flash-investigation). [CGS connection declarations](https://github.com/NUIKit/CGSInternal/blob/master/CGSConnection.h) describe nesting; [yabai's declarations](https://github.com/asmvik/yabai/blob/master/src/misc/extern.h) and [usage](https://github.com/asmvik/yabai/blob/master/src/window_manager.c) provide the SLS binding precedent. Do not substitute AppKit's `disableScreenUpdatesUntilFlush`: current SDK headers mark it a no-op.
- Do not replace this with Tauri 2.11.6 `set_effects(None)`: its macOS clear branch is missing, and its apply path discards native helper errors. Main-thread apply/remove work is awaited via oneshot; errors return to the frontend. Raw native handles never cross threads.
- Pinned Tauri 2.11.6 requires the `macos-private-api` feature / `macOSPrivateApi` configuration for transparent WKWebView backing. This is a distribution constraint if a future Mac App Store target is considered; no Tauri upgrade or signing-policy change is included here.
- Read `NSWorkspace.accessibilityDisplayShouldReduceTransparency` on the main thread. Enforce it natively by applying radius 0; frontend capability replies keep all surfaces opaque while retaining preferences. Refresh capabilities on native window focus (not a polling timer), including after visiting OS Settings. Also honor the browser's reduced-transparency media query where available.
- Linux exposes whole-window opacity, sends no native effect calls, and leaves blur to the compositor. Static native capability expresses our transparent-backing implementation, not a detected guarantee of desktop compositor support. No universal blur protocol or desktop-specific settings mutation.
- Windows/other targets keep opaque windows and disabled transparency controls. No parity commitment.

## Code map and performance/lifecycle

- `src/window-appearance.ts`: pure schema/defaults, density calibration and RGBA conversion. `src/window-appearance-controller.ts` owns controls/optimistic edits, the no-op paint signature, media/capability readiness and explicit theme subscription. `src/window-appearance-effects.ts` owns one serial typed latest-value pipeline and per-stage failure/cache/settlement; unchanged broadcasts do no native work. See [Window presentation](window-presentation.md) for change routing. Theme previews remain window-local; opacity/blur previews are global paint-only state.
- `src/button-surfaces.ts`: filled-control colour pairing, bounded-underlay contrast and palette-derived density floors; no theme IDs, DOM, IPC or persistence.
- `src/native-window-appearance.ts`: shared appearance-preview subscription/snapshot/latest-value publisher and native IPC/focus adapter and shared CSS import. Install in `src/settings-surface.ts` for project/welcome/global Settings, and `src/popout.ts` for references. Startup capability reads do not gate session/plugin boot. Only cold global Settings waits on first appearance/zoom settlement before native reveal. Dispose observers, media listeners, native focus listeners and stale replies on unload.
- `src/window-appearance.css`: Nimrod-specific alpha surface tokens derived from original theme tokens. No palette rewrite, container `opacity`, CSS `backdrop-filter`, per-card blur, transcript mutation or new scroll owner. Continuous role-derived interaction/panel overlays are separate from the base tint; `transcript.css`, `theme.css`, `workspace.css` and `application-notices.css` consume shared semantic control fills with their exact opaque palette fallbacks; native blur adds no material tint at zero theme opacity.
- `src/preferences.ts` / native `preferences.rs`: global getters/saves and matching validation; reuse the established preference writer rather than direct file edits or state writes. Theme presentation is published once after `applyTheme`; unrelated root styles and the controller's own mutations do not cause native work.
- Appearance errors are application-owned, routed through the existing notice strip with separate cause IDs for capabilities, native effects, focus observation and each setting's save. An unrelated success does not clear another failed operation. No field-error bubble or new notification surface.

## Native enable-flash investigation

The explicit standalone [blur probe](../../../../tools/blur-probe/README.md) reproduces a single captured flat-grey backdrop frame at 0→7, followed by correct blur, on macOS 27.0.1 (26A434), Apple Silicon. It runs static AppKit and transparent WKWebView targets over a synthetic checkerboard, with an unchanged third window. Both targets reproduce the flash; the control stays stable. No grey frame was captured at 7→20 or nonzero→0. Thus the native WindowServer blur-enable path alone is sufficient: no Nimrod Settings, DOM, theme/tint, harness or multi-window broadcast is required. The global preview makes every project window independently take that transition; the probe does not show one setter flashing an unchanged peer.

The existing connection update batch, alternate style 0, disabled shadows, increased backing alpha, whole-window alpha, opacity hints, explicit redraw/CATransaction flush, disabled AppKit auto-flattening and setup-time rehosting all still reproduce it. Do not promote any as a verified fix. No production code or blur semantics changed in this investigation. The precise internal WindowServer bug is not established; alternate native backdrops remain research, not an adopted backend or a promise of flicker-free rendering. Zero must remain genuinely sharp, without an invisible nonzero minimum or screenshot overlay.

Window-filtered ScreenCaptureKit recording replaces nonzero legacy blur with a persistent grey substitute and is **not** useful for visual blur acceptance. Actual evidence comes from cropped display capture inside the probe's opaque elevated synthetic backdrop; no Nimrod/user-session content or audio was recorded. The probe requests 60 Hz, but PNG writing may drop frames; single-frame observations are not exact timing measurements, and missed flashes are not passes. The tool README retains the experiment matrix and a synthetic before/grey/blur contact sheet. This is native reproduction evidence on one OS/build, not packaged Nimrod acceptance, a Linux result or a blanket macOS compatibility claim. [Contributing](../../../../CONTRIBUTING.md#native-blur-diagnostic) owns the explicit setup/run entry point.

### Ghostty/Zed upstream follow-up

The [pinned source comparison and native experiments](../../../../tools/blur-probe/upstream-comparison.md) traced live updates, not just startup. Ghostty still uses the same numeric WindowServer setter; its thread-default connection (equal to the main ID in our probe), white .001 backing and repeated native appearance setup all still reproduce the flash when transplanted into the fixture. Its visibility fixes and unrelated tab/resize issues do not establish an enable-flash fix.

Current Zed instead creates/removes an `NSVisualEffectView` for live existing-window Settings changes, using `UnderWindowBackground`/`BehindWindow`/`Active` and private layer cleanup to remove tint/saturation. A native fixture of that policy showed no captured grey activation frame. Our **separate experimental extension**, not Zed upstream behavior, copies/replaces its Gaussian filter to drive numeric strength: three runs, 18 target enables and 2,215 captured frames showed no detected grey frame while an interleaved original-setter control still flashed. Pixel/image comparison confirmed distinct 7/20 strengths, actual colored backdrop sampling and sharp zero after effect removal. In-place filter mutation initially produced identical 7/20 pixels despite successful native property assignment; copying/replacing the filter was necessary in the tested setup.

This is an experimentally supported integration direction, **not a production fix**. Native title-bar coverage (the fixture covers only content), full opacity/theme/accessibility behavior, private filter capability/fallback/lifecycle handling, corners/resize/fullscreen and streaming performance remain gates. Capture can drop frames. No requirement to retain a warm nonzero radius follows from the successful fixture; live removal/reinsertion was exercised. The production boundary above remains unchanged, including its current prohibition on private layer-tree edits, until a deliberate backend integration changes that contract.
