# Window translucency

**Status: implemented; targeted TypeScript/Rust/offline WebKit coverage passes; native acceptance pending.** User guide: [Translucency](../../../../docs/translucency.md). Related: [Themes](themes.md), [Preferences](preferences.md), [Settings layout](settings-layout.md), [Verification](verification.md).

## Contract and schema

Global-only paint preferences, separate from color-theme selection:

| JSONC key | Values | Default |
| --- | --- | --- |
| `appearance.backgroundOpacity` | integer 0–100 | 100 (opaque) |
| `appearance.frostedBackground` | boolean | true |
| `appearance.translucencyArea` | `window` / `chrome` | `window` |

TypeScript and Rust validate all three. Explicit nulls are invalid. Project files reject these keys as global-only; no migration or automatic writes. Existing comment-preserving queued/CAS preference writes and revision-ordered broadcasts own persistence. Original theme palette tokens remain unchanged; derived filled-button roles repair unreadable pairs without theme-ID exceptions; true frosting at opacity 100 does not install a material. Native macOS title bars deliberately follow the theme instead of the previous system/wallpaper-tinted fill.

Global Settings exposes the opacity slider, area selector and (only with native frost capability) frosting checkbox. Project settings hides the entire control group, while its window still follows the global appearance. Opacity `input` previews Settings immediately and broadcasts paint-only opacity to project/reference windows; `change` commits once; area/toggle edits apply immediately and save. Pending per-field previews survive older broadcasts/save completions; a failure discards only its matching local edit, never a newer one. No automatic save retry, window recreation, harness calls or navigation.

`chrome` means Project bar/Session sidebar, or Settings header/category sidebar. Conversation, empty/welcome content, Settings content and pop-outs remain opaque. `window` makes those base surfaces translucent too. Pop-outs have no application chrome, so `chrome` keeps their entire content background opaque. Code, ordinary dialogs, suggestions and user-turn backgrounds retain solid backing surfaces. In whole-window mode, role-derived interaction/panel overlays keep the Status area and notices denser than the conversation while changing continuously with the slider. Application notices paint a corresponding denser single surface because they have no tinted parent. Shared primary/secondary/hover/selected/danger button fills follow the same endpoint-continuous policy; chrome-only scopes these tokens to Project bar/sidebars/Settings header, leaving conversation buttons unchanged. Filled primary/secondary/danger controls keep a stable opaque foreground, and derive sufficient fill density for contrast through the shared [filled-control policy](#filled-control-contrast). Do not interpolate opposite foreground colors. Text/icon opacity, notice error borders/icons, focus rings and interaction geometry remain unchanged; disabled controls retain their existing dimming.

The full-window Settings dialog/backdrop is transparent in either translucent mode; underlying Project bar/workspace are `visibility:hidden` only while that Settings dialog is open, retaining layout, scroll geometry and mounted controllers. Each Settings surface paints its own tint exactly once; the modal must expose the native backing, not the conversation under it. Ordinary dialogs retain existing solid backgrounds/backdrops.

## Visual hierarchy across the opacity range

**Invariant: preserve the same visual hierarchy throughout the slider's range.** Translucency changes surface density progressively, not the identity of surfaces. Status area/session notices must remain distinguishable panels below 100%, rather than collapsing into the conversation's background. Buttons and their hover/selected states keep their emphasis ordering. Crossing 100 → 99 must not switch to a visibly different low-density recipe.

- Base content follows the slider directly. Interaction overlays are lighter than Status-area/notice overlays; a panel composited over a base must remain denser than that base at every value below 100. At 100, all fills are opaque and palette color contrast preserves the hierarchy instead of alpha differences.
- All role curves are continuous and monotonic, converge to alpha 1 at the opaque endpoint, and reproduce the opaque presentation there (original palette pairs where readable; repaired filled-control pairs otherwise). Do not use fixed low button fills or `opacity × 0.2` panels for every value below 100: those create an endpoint discontinuity. Do not multiply the container's opacity, fade text, or reintroduce an 85%-opaque overlay over an already tinted base.
- `windowSurfaceOpacities` owns the current calibration: normalized slider `p = opacity / 100`, endpoint easing `e = p^8`, overlay role `a = minimum + (1 − minimum) × e`. Baseline low-end minima: interaction/secondary 0.10, Status-area/notice panels 0.25, primary 0.35, primary hover/selection/danger 0.45, secondary/toolbar hover 0.30. Filled-button minima are additionally raised by the contrast policy below; these baseline curves are not a contrast guarantee. These floors retain hierarchy at a clear base; easing keeps intermediate settings modest while smoothly approaching the original opaque palette. At 65%, interaction/panel overlays are about 12.87% / 27.39%, giving a session notice ~74.6% effective alpha over the 65% base, not the base's same transparency. Status composes over the interaction area as well.
- A parent/base with alpha `p` plus overlay `a` has effective alpha `p + (1 − p) × a`. The fixed-position application strip uses this effective notice alpha as its own single fill. Never apply the base tint again at each nesting level. Preserve every consumer's original palette recipe (including distinct primary/danger foregrounds, secondary/control hover, list/quick-input/suggestion selection fallbacks).
- Native frosting remains a separate OS-owned backdrop; neither toggling it nor selecting a theme changes the CSS hierarchy calibration. Code, ordinary dialogs and suggestions remain explicit solid-backing exceptions. Chrome-only continues to preserve the conversation's opaque appearance. Reduce Transparency restores opaque fallbacks without changing saved preferences.
- Acceptance: inspect 100, 99, 95, 85, 65, 50, 25 and 0 with both dark/light palettes. Panels must not disappear just below 100; lowering opacity preserves their ordering and recognizable treatment. Native desktop/material contrast still needs user acceptance; DOM/math fixtures establish the implemented curves, not native visual quality.

## Filled-control contrast

`src/button-surfaces.ts` owns palette-independent pairing for primary, secondary and danger buttons (including hover). Preserve the supplied text colour if it has at least 4.5:1 contrast against the solid fill; otherwise use a readable neutral. Button-specific colour roles are opaque RGB, even if the source palette supplies alpha. Never rewrite `--vscode-*` tokens or branch on theme IDs. Incompatible hover hues use the normal hue and stronger hover density so the same text remains readable. Secondary control hover retains its normal hue rather than interpolating unrelated fill colours.

Calculate a minimum fill alpha sufficient for that text over **any** sRGB underlay: use the composited black/white luminance interval; if the foreground falls inside it, an intermediate underlay can give contrast 1. Binary-search the safe alpha, then use `floor + (1 - floor) × p^8`, with `floor` the larger of this contrast minimum and the existing role minimum. Hover density is never below its normal state. This preserves continuous/monotonic density and avoids mixed, low-contrast label colours. Some buttons necessarily stay denser at low window opacity; do not reduce the floor just to match another role's numerical alpha. Existing panel/interaction curves are unchanged. Valid solid opaque pairs keep their colours; originally unreadable/alpha button pairs are repaired at the opaque endpoint too. Disabled-control dimming remains intentional. Transparent toolbar icons and ordinary text retain their existing treatment; this is a filled-control contrast policy, not native accessibility certification.

Recompute palette roles only at installation, explicit completed theme publication or inherited-system scheme changes. The applied-theme snapshot includes a palette signature, so changed button colours with the same ID/background also invalidate presentation. Slider ticks only update density; unchanged state broadcasts do no palette/style reads.

## Live opacity preview

The native `SettingsWindow` owns one ephemeral, generation-authorized, revisioned `{revision, opacity}` snapshot. Only its current frontend may call `preview_window_opacity`; all window types subscribe/read through `native-window-appearance.ts`. Opacity is bounded 0–100, or null to clear. Subscribe before fetching the initial snapshot; reject stale replies/events. Newly opened project/reference windows read the current preview. This state is not JSONC, a theme preview, a project override or a harness event.

The frontend coalesces unsent slider values through one serialized latest-value publisher, while painting Settings locally immediately. Commit success/failure clears only its matching edit; older completions cannot cancel a newer drag. Native Settings destruction clears the preview and rejects late old-generation commands, including when unload IPC cannot run. An uncommitted close restores saved opacity. File writes still use the existing preference writer once on `change`; no per-input persistence, focus/navigation, window recreation or session work.

## Native title bars and first presentation

macOS uses native **Transparent** title-bar style, not Overlay or custom HTML chrome. Keep the title, traffic lights, window drag/resize, native menus/cycling and the separate 48 CSS-pixel Project/Settings header. The native title-bar tint follows that window's editor-background/Project-bar colour and effective background opacity (opaque under Reduce Transparency), including same-dark/light-mode theme previews and restoration. Caption/text appearance follows the explicit theme mode even when frosting is off; Nimrod (system) keeps inherited native appearance.

`titlebarTint` converts the allowlisted 3/4/6/8-digit hex colour to bounded sRGB RGBA bytes. The single typed frontend appearance pipeline serializes/coalesces material then title tint, and skips unchanged colour/opacity/appearance-identity requests. Material and tint no longer overlap independent queues; appearance identity is part of the tint cache so older same-colour work cannot suppress retinting a rebuilt title view. Slider and same-mode palette changes do not reinstall blur. Successful tint is refreshed on native activation; failures remain separately owned/deduplicated and are not silently retried on state broadcasts. The explicit `applyTheme` snapshot detects same-mode palette changes. No root-style observer or presentation inference from DOM mutations is used.

`window_appearance.rs` dispatches `tint_window_titlebar` only against its invoking window on the main thread; AppKit implementation is isolated in `macos_window_appearance.rs`. Prepare native layout, use the standard Close button's public NSView ancestry, and tint only a full-width, title-height (≤120pt) existing view layer. Do not change the NSWindow's clear backing to a solid theme colour—that would destroy content transparency. No inserted hit-test view, moved controls, title hiding, full-window overlay or geometry mutation. Bounded unsupported/full-screen hierarchies retain transparent native chrome; their precise native tint/resize/full-screen behavior needs acceptance. Linux/possible Windows title decorations are not changed.

Cold **global Settings** exposes `ready`/`settled` and remains natively hidden until the mounted palette/appearance/title-tint/zoom state is prepared. Initial effect failures settle to the error/fallback presentation, not a permanently hidden window. [Settings layout](settings-layout.md#first-native-presentation) owns the generation-scoped, idempotent reveal and its narrow optimistic-policy exception. Project and reference-window startup are not newly gated.

## Native boundary and platform scope

- `src-tauri/src/window_appearance.rs::prepare` is composed by `window_presentation.rs::prepare`, alongside—but separate from—the navigation guard; all welcome/project/Settings/pop-out constructors pass it. macOS/Linux backings are transparent from creation, but opaque CSS remains the initial/default state. No runtime window replacement, geometry mutation or focus action.
- Native commands report `{platform, transparency, frost, reducedTransparency}` and apply only to the invoking `WebviewWindow`, never a frontend-provided label. No process/session privileges or OS/compositor configuration.
- macOS uses the already-locked `window-vibrancy` 0.6 helper directly: semantic `Popover` material (selected to avoid the initial dense Sidebar fill), `BehindWindow` blending (helper-owned), `Active` state, theme-selected **window-local** native dark/light appearance. Theme tint is CSS; material blur strength is OS-owned. Remove the tagged helper view before reapplying, so theme previews cannot stack materials. Disabling frosting/opaque mode calls actual `clear_vibrancy`; that NSWindow's explicit appearance remains theme-matched for native title/text, while the system scheme leaves it inherited. Use `NSWindow.setAppearance`, never Tauri/Tao `set_theme`: the pinned macOS implementation sets NSApplication appearance, leaking window-local previews across windows. Resolve/use the NSWindow pointer on the main thread; keep it non-opaque with a clear background. Native apply receives `dark: boolean | null`: explicit theme modes override just that window; `null` for Nimrod (system) leaves native appearance inherited, otherwise the override can pin WebKit's media query and stop following OS changes. Native recipe density remains OS-owned, not measured by source fixtures.
- Do not replace this with Tauri 2.11.6 `set_effects(None)`: its macOS clear branch is missing, and its apply path discards native helper errors. Main-thread apply/remove work is awaited via oneshot; errors return to the frontend. Raw native handles never cross threads.
- Pinned Tauri 2.11.6 requires the `macos-private-api` feature / `macOSPrivateApi` configuration for transparent WKWebView backing. This is a distribution constraint if a future Mac App Store target is considered; no Tauri upgrade or signing-policy change is included here.
- Read `NSWorkspace.accessibilityDisplayShouldReduceTransparency` on the main thread. Enforce it before installing native frosting; frontend capability replies keep all surfaces opaque while retaining preferences. Refresh capabilities on native window focus (not a polling timer), including after visiting OS Settings. Also honor the browser's reduced-transparency media query where available.
- Linux exposes alpha and area controls, sends no native effect calls, and leaves blur to the compositor. Static native capability expresses our transparent-backing implementation, not a detected guarantee of desktop compositor support. No universal blur protocol or desktop-specific settings mutation.
- Windows/other targets keep opaque windows and disabled transparency controls. No parity commitment.

## Code map and performance/lifecycle

- `src/window-appearance.ts`: pure schema/defaults, density calibration and RGBA conversion. `src/window-appearance-controller.ts` owns controls/optimistic edits, the no-op paint signature, media/capability readiness and explicit theme subscription. `src/window-appearance-effects.ts` owns one serial typed latest-value pipeline and per-stage failure/cache/settlement; unchanged broadcasts do no native work. See [Window presentation](window-presentation.md) for change routing. Theme previews remain window-local; opacity previews are global paint-only state.
- `src/button-surfaces.ts`: filled-control colour pairing, bounded-underlay contrast and palette-derived density floors; no theme IDs, DOM, IPC or persistence.
- `src/native-window-appearance.ts`: shared opacity-preview subscription/snapshot/latest-value publisher and native IPC/focus adapter and shared CSS import. Install in `src/settings-surface.ts` for project/welcome/global Settings, and `src/popout.ts` for references. Startup capability reads do not gate session/plugin boot. Only cold global Settings waits on first appearance/zoom settlement before native reveal. Dispose observers, media listeners, native focus listeners and stale replies on unload.
- `src/window-appearance.css`: Nimrod-specific alpha surface tokens derived from original theme tokens. No palette rewrite, container `opacity`, CSS `backdrop-filter`, per-card blur, transcript mutation or new scroll owner. Continuous role-derived interaction/panel overlays are separate from the base tint; `transcript.css`, `theme.css`, `workspace.css` and `application-notices.css` consume shared semantic control fills with their exact opaque palette fallbacks; native frosting at zero theme opacity still retains OS material tint.
- `src/preferences.ts` / native `preferences.rs`: global getters/saves and matching validation; reuse the established preference writer rather than direct file edits or state writes. Theme presentation is published once after `applyTheme`; unrelated root styles and the controller's own mutations do not cause native work.
- Appearance errors are application-owned, routed through the existing notice strip with separate cause IDs for capabilities, native effects, focus observation and each setting's save. An unrelated success does not clear another failed operation. No field-error bubble or new notification surface.
