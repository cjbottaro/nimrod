# Notifications: implementation reference

**Status: implemented.** This reference owns current specifications and implementation details. [Verification status](verification.md) separates fixture evidence from native acceptance; [historical records](history/feature-records.md#notifications) retain prior execution records.

Read the [human guide](../../../../docs/notifications.md) and [architecture](architecture.md). Paths below are repository-root relative.

## Specification and acceptance criteria

Live background completion/input/failure triggers passive delivery; only an explicit valid click navigates the exact still-open runtime target to bottom. Native focus/lifecycle/preferences revalidate at dispatch, and historical/stale events never replay.

## Code map

- `src/pi/session.ts`: Pi-specific attention callback (`completed`, `input`, `failed`), live-run/outcome/latest-finalized-assistant-text tracking, input-dialog queue, disconnect deduplication.
- `src/main.ts`: captures originating tab/token; lifecycle eligibility; notification-safe explicit name; Settings toggle; completion unread marker; window-targeted click listener with runtime ID/token revalidation and shared selected-session loading/reconnect.
- `src/notifications.ts`: testable policy; initial native focus filter, optional permission preparation, final focus/lifecycle/preference/selection revalidation, latest-attempt status; bounded Markdown-to-plain-text response previews using marked/DOMPurify with all but line-break tags stripped.
- `src/preferences.ts`, `src-tauri/src/preferences.rs`: validated boolean `notifications.enabled`, default true, existing JSONC/CAS writer and cross-window synchronization.
- `index.html`: Settings → Notifications, On/Off selector, Send test notification and Refresh notification diagnostics buttons plus last-attempt/native-policy status. Errors also use the existing project error area.
- `src-tauri/src/notifications.rs`: narrow native command; project-window registry authorization, native settings/exit/focus checks, bounded labels, completion preview validation/truncation and generic input/failure bodies; process-local click envelope and project-authorized focus command.
- `src/pi/transcript-scroll.ts`, `src/pi/webview-client.ts`: explicit bottom-navigation API, restores follow intent and reconciles selection/layout without changing ordinary switching.
- `src-tauri/src/linux_notifications.rs`: direct notify-rust submission, literal/escaped preview body, default open action and async action waiter.
- `src-tauri/src/macos_notifications.rs`: macOS-only UserNotifications backend, real bundle validation, main-thread operations, retained foreground/click delegate, authorization handling and awaited submission callbacks (errors identify authorization versus submission).
- `src-tauri/tauri.conf.json`, `mise.toml`, `scripts/verify-macos-bundle.ts`: whole-bundle local macOS ad-hoc signing and post-build signature/identity/Info.plist/resource verification. Pure signature fixtures live in `test/bundle-signature.test.ts`.
- `src-tauri/src/main.rs`, `src-tauri/Cargo.toml`: app-owned prepare/send/test/diagnostics commands and startup delegate installation; macOS objc2 UserNotifications/Foundation/block2 dependencies. Linux uses a target-specific direct notify-rust dependency; Windows retains the Rust Tauri notification plugin. No JS notification plugin dependency/capability grant.

## Invariants

- Pi owns semantic lifecycle. Only a live `agent_start` followed by idle `agent_settled` generates completion; no history, `agent_end`, tool result, ordinary snapshot, compaction-only operation or duplicate settled alert.
- Latest assistant `message_end.stopReason` determines failed/completed at settlement; errors during retries do not notify prematurely. Aborted runs and explicit Stop suppress completion. Tool errors alone do not imply session failure.
- `process_error` generates failure once per coordinator; disconnect flag rejects subsequent old events. Shell suppresses intentional close/restart/unload and native exit state suppresses quit dispatch.
- Input attention occurs when an actual supported extension dialog enters the serialized dialog queue, not when an ordinary extension `notify` arrives or a local model/name picker opens. Notification does not alter existing dialog/focus behavior.
- Capture tab/token; never target whatever session becomes active after an await. Recheck validity, preference and selection after native `isFocused`, and repeat after `prepare_notifications` (an OS authorization prompt can remain open). Recheck project registration off the main thread, then selected/native focus, window presence and preferences on the actual native dispatch thread. Old tokens, closing/restarting tabs and unloading windows cannot dispatch late alerts. No replay or retry.
- Background includes another session in the same focused window, another project window, an unfocused selected session, Settings covering the selected conversation, or the remembered session hidden by Unread or Working. Shell selection/unread policy uses the presented conversation, not the remembered navigation target. The owning project window's native focus matters, not app-wide activity or webview visibility alone.
- Never use `tab.title` in banners: fallback sidebar titles contain prompt excerpts. Explicit Pi `sessionName` or generic “Session” only. Native project name derives from the calling window's canonical registered directory, not frontend input. Completion body may contain the latest finalized assistant response, including paths/content the assistant authored; never use user-message, thinking or tool-result records. Input/failure bodies remain generic, without dialog title or raw errors.
- Banner title is `project · session`, without a redundant Nimrod prefix; OS chrome/icon supplies application identity. Native labels remove control/bidi formatting characters and cap at 100 Unicode characters. No custom sound or secondary actions; Linux registers the standard default open action. The explicit Settings test is the only intentional focused-session-policy bypass; it uses fixed text and still honors native project/exit/preferences guards. Notification IPC never starts/resumes/stops processes or acknowledges/submits prompts.
- Settings save failures keep last committed policy, report alongside the control, and restore the picker. Invalid external edits retain last valid settings. Default on is independent of OS permission; no claim of granted/delivered status.

## Product decisions: notification clicks

- **Click → owning project window → exact open session → transcript bottom.** Do not implement response-start anchors or a fit-in-viewport heuristic. Always bottom; re-enable auto-follow using the existing scroll owner. Normal session switching keeps its saved reading position.
- Delivery remains passive. Navigation is an explicit user click, not completion-driven selection.
- Scope is sessions still open in this app run, including temporary sessions and disconnected sessions with retained transcript. Never reopen closed/deleted sessions, replay prompts, or route to an arbitrary active/latest/named session. A valid click explicitly selects its still-open target and loads/reconnects saved history if disconnected, subject to lifecycle/deletion guards.
- Runtime session ID plus launch token selects the target, not display name or session-file discovery. A restart retires the old token. Previous-process notifications are ignored even if the OS launches/activates Nimrod.
- Explicit navigation reveals filtered targets (switching to All only when required), clears unread through existing selection semantics, and does not update last-used recency. Dismiss shell Settings/palette where modality permits; never answer/cancel Pi dialogs.
- Same policy on macOS and Linux, narrow native callbacks per platform. Windows remains possible future support, not a parity promise. Linux service action/compositor focus support is variable; tests/build on macOS are not native Linux acceptance.

### Click routing implementation

Each session dispatch carries `target: {session: tab.id, token}`, alongside a separate notification-safe display name. Rust serializes a request identifier containing an event UUID, per-process random identity, owning window label and target. No path/response/name is needed for navigation and no routing map/app-state migration is added. Each event UUID keeps repeated session alerts distinct.

macOS installs `didReceiveNotificationResponse:withCompletionHandler:` on the existing delegate. Only Apple's default action routes; dismissals and test requests do not. Complete the OS callback exactly once, then extract/route owned identifier data using the retained app handle. Requests from earlier processes fail the envelope identity check.

Linux bypasses the Tauri notification plugin for send/test. Direct `notify-rust` uses its `z-with-tokio` backend feature (serde plus the existing Tokio runtime), awaits `show_async` (submission errors reach the shell), registers `default` / “Open session” for targeted alerts and retains the handle in an async action waiter. Action/closure/service disconnect ends the waiter; app exit ends remaining tasks. No blocked worker per notification, no desktop permission guess, no timeout-driven navigation/replay. Windows stays on the old plugin path without click support. Compositors may reject window activation; no Wayland activation-token integration is implemented yet.

Native callbacks emit `nimrod-notification-click` only to the named WebviewWindow and do not focus it themselves. The frontend listener must also be WebviewWindow-targeted (Any listeners receive other windows' targeted emissions). Validate open membership/token/lifecycle/deletion before calling `focus_notification_window`, then revalidate after its await. A newer notification click or explicit session/sidebar-view navigation wins over an older delayed focus result. Focus failures are reported but do not prevent exact-session selection.

Notification selection uses `activate(..., 'notification')`, sharing normal saved-session loading/reconnect while retaining reveal/focus semantics. Retired launch tokens remain invalid; a reconnect retires the notification's old token. `PiView.scrollToBottom` delegates to `TranscriptScroll`, clears interrupted follow intent, jumps immediately after presentation and requests a layout-settled frame through the existing scheduler. Reader wheel/touch/key intent can still cancel that frame.

Test alerts have no target and cannot select a session. Native OS activation may still occur for stale/test alerts, outside Nimrod's router.

## Response preview pipeline

`SessionUi.attention(kind, response?)` supplies response text only for completed runs. Each `agent_start` clears it; each assistant `message_end` replaces it with string content or joined `type: text` blocks, limited to 16,384 UTF-16 units. An empty latest assistant message yields no preview rather than stale earlier narration. Streaming deltas/history/user/tool messages do not set it. Failed/aborted runs never disclose it.

The shell captures the originating response alongside its tab/token. `notificationPreview(window)` renders the bounded source through marked, strips tags/attributes with DOMPurify (only inert line breaks retained temporarily), extracts text, removes controls/bidi formatting, compacts whitespace and bounds at 1,000 Unicode characters. Longer previews use 999 characters plus an ellipsis. No media, live HTML or link destination is inserted into the app. Conversion failure falls back to the generic body rather than disrupting Pi event delivery/acknowledgements. The normal native dispatch receives optional `preview`; no new model/session query or persistence is added. The OS chooses actual visible line/character capacity; never promise a universal banner size.

Native `body(kind, preview)` accepts previews for completed alerts only, independently normalizes/sanitizes/bounds at 1,000 Unicode characters, and falls back to “Agent finished.” if empty. Input/failure previews are ignored even if passed over IPC. Linux body text is markup-escaped because desktop services may interpret notification markup; macOS/Windows receive literal plain text. OS Notification Center/lock-screen retention may contain assistant text under existing OS policy. No separate preview preference is implemented; the existing On/Off toggle controls all alerts.

## Storage and platforms

`notifications.enabled` is an optional flat boolean in user JSONC settings. No new app-state keys, migrations, Pi writes or project overrides. Omission defaults true on both sides. Uses existing revision ordering, atomic writes and external-edit polling.

Platform direction remains macOS first, Linux next, Windows possible later. macOS now uses Apple's UserNotifications framework directly. Linux uses direct notify-rust/zbus for desktop default-action routing and awaited submission; Windows retains Tauri's notify-rust backend, whose pinned 2.4 implementation asynchronously ignores downstream delivery errors. Desktop permission state is not a reliable reflection of OS authorization. Do not wire mobile `onAction` APIs and claim desktop routing.

### macOS backend replacement and diagnostics

The former plugin path returned Ok before downstream dispatch and swallowed notification/application-identity errors. macOS uses the native backend below to surface authorization/submission failures; historical presentation investigation belongs in [notification records](history/feature-records.md#notifications).

The legacy hook file is removed. macOS session alerts now bypass that plugin path entirely, using `UNUserNotificationCenter` without NSBundle swizzling or Terminal/Finder identity borrowing. The plugin remains registered, but only the Windows send/test path calls it; macOS/Linux use their narrow native backends. `center(identifier)` verifies the actual main bundle matches Tauri's identifier before accessing the singleton (unbundled calls can raise Objective-C exceptions). All center operations are scheduled through Tauri's main thread. A main-thread `OnceCell<Retained<NotificationDelegate>>` keeps the weak delegate alive; unexpected existing delegates fail rather than losing somebody else's callbacks.

`notifications::initialize` now runs during Tauri setup, before window creation, rather than first attaching the delegate during a late test/run completion. Packaged matching-bundle processes call `center()` and retain the delegate then; unbundled dev executables skip this initialization and still report the packaged-app requirement on an attempted send. Integration initialization errors are nonfatal to app startup and are rechecked/reported by subsequent commands. Startup does not request authorization or post anything. Moving registration earlier follows [Apple's explicit pre-launch delegate requirement](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate); do not claim it fixes foreground delivery without native evidence. Source ordering was checked in the pinned Tao/Tauri stack: macOS `applicationDidFinishLaunching` calls `AppState::launched`, which synchronously dispatches NewEvents(Init); Tauri runs its setup on runtime Ready. Keep initialization in that startup path, not a queued frontend command.

The objc2 delegate implements `userNotificationCenter:willPresentNotification:withCompletionHandler:` and calls its completion exactly once with Banner | List, never Sound/Badge. Foreground presentation does not navigate. Click routing uses the default action callback and opaque request identifier; no custom macOS actions/userInfo are added. System styles, Focus and lock-screen policy remain authoritative.

`prepare_notifications` authorizes only registered project windows. macOS preparations are serialized by an async mutex: read actual UN authorization settings; request Alert authorization only if NotDetermined; reject Denied/unknown states explicitly. First-time permission handling precedes the shell's final focus/selection/lifecycle revalidation, so a long permission prompt cannot dispatch a retired/read originating session. Authorized preparations do not re-prompt. The command performs no Pi operation.

`notify_session` returns `submitted` or `suppressed`; the native macOS send validates immutable window/project ownership off-main (the router holds its registry while awaiting main-thread window creation), then rechecks exit/preferences/window/focus on the actual dispatch thread, builds a uniquely identified immediate request (a process-local click envelope for session alerts, plain UUID for tests), and awaits `addNotificationRequest`'s completion/error callback. Only owned strings/primitives cross callback/async boundaries. Completion-channel state tolerates duplicate/late callbacks. Settings/submission waits time out after 10 seconds, authorization after 120 seconds; no automatic retry/replay. A queued main-thread task does not start if its receiver already timed out. Already-submitted timeout is ambiguous, not proof that the OS rejected it.

`notification_diagnostics` is project-window authorized and read-only: no permission request, dispatch, session access or preferences write. macOS reads actual UN authorization/alertStyle/alertSetting/notificationCenterSetting plus `NSApplication.isActive()` on the main thread, then formats only owned metadata. `FOREGROUND_CALLS` is a process-local atomic counter incremented exclusively in the actual `willPresentNotification` callback before the immediate Banner | List completion. Counts aggregate all project windows and reset with the process; a snapshot's zero is not proof a future/pending callback cannot occur. Refresh after accepted delivery, rather than inferring a per-request receipt from this counter. Non-macOS returns an explicit diagnostics-unavailable description, not guessed policy.

The shell automatically reads diagnostics after an accepted manual test, and exposes a separate refresh button even while alerts are Off. Reads/test actions are serialized through their disabled controls; diagnostic failure appends to the already-accepted test status, never relabels it a delivery failure or marks a Pi session failed. A manual refresh itself never runs prepare/send or starts/stops a child. No timers/polling, persisted counters, live response content, OS notification-setting changes or focus/navigation are introduced.

The Settings test uses the same authorization/dispatch path with fixed `project · Notification test` title and fixed body, passing selected=false by explicit user action. It does not start an agent, make a model request, inspect a session, or change notification preferences; Off disables the button and native guards still apply. Latest session status distinguishes quiet reasons, preparation, submitting, accepted submission, native suppression and errors. macOS errors are copied into both Settings and the existing project error area; no session failure or Pi acknowledgement is inferred.

### Native signing and presentation pitfalls

UserNotifications requires whole-bundle signing: linker-only ad-hoc executable identity can fail despite OS permission. The explicit build task verifies identifier, bound Info.plist and sealed resources. Local ad-hoc grants may change after rebuilding; Developer ID/notarization is separate work. Never mutate OS permission databases or sign a running bundle in place.

On macOS 27.0.1, user-confirmed signed test alerts reached Notification Center and Persistent foreground presentation; Temporary presentation remained inconsistent despite delegate callbacks and Banner/List flags. Cause remains unproven. Do not infer missing delegates from an immediate zero callback counter, override OS style or apply urgency workarounds. See [investigation history](history/feature-records.md#macos-27-investigation) for native logs and signing diagnosis, and [current acceptance](verification.md).

Unbundled executables report a packaged-app requirement rather than borrowing another app's identity. Linux service action/focus and possible Windows installed identity remain native acceptance gaps.

## Tests and verification

- `test/session.test.ts`: intermediate/duplicate settled suppression, aborted runs, final errors and successful retries, extension input versus ordinary notices, disconnect deduplication, existing acknowledgement/queue semantics, latest-finalized-response extraction, run resets and failure exclusions.
- `test/notifications.test.ts`: foreground/background focus policy, disabled/retired targets, selection/focus/lifecycle/settings changes during authorization, authorization failures/native suppression status, nonfatal errors, plain-text Markdown conversion, unsafe HTML/media stripping and Unicode-safe preview bounds.
- `test/shell.test.ts`: actual shell with mocked native boundary; background/selected/unfocused routing, generic labels despite private prompt titles, completion previews without reasoning, intentional-close suppression, persisted/off/external settings and input-dialog alerts without process interruption; explicit All/Working → Completed dispatch status; manual test/off policy with no process commands, read-only refresh while Off, metadata display, nonfatal diagnostics lookup failure and native errors in Settings/project error surfaces. Click tests cover exact identity, cross-window isolation, retired tokens, closed/disconnected targets, filtered reveal, draft preservation, unread clearing, Settings/palette dismissal, bottom override and selected-session reconnect without prompt submission.
- `test/preferences.test.ts`: default, JSONC preservation, boolean validation, last-valid retention.
- Rust notification tests: bounded/sanitized labels, completion preview normalization/truncation/fallback, generic input/failure bodies and enum validation; native preferences tests validate boolean settings. Routing envelopes test exact targets, event uniqueness and malformed/previous-process rejection.
- `test/browser/workspace-tabs.spec.ts`: offline All/Working → Completed captures preparation/send/status, and Settings test/off/read-only-refresh policy never starts/stops extra agents or emits another notification. Native notification commands are mocked, never delivered. Real WebKit coverage verifies notification bottom override versus ordinary reading-position preservation at fractional zoom, filtered reveal and Settings dismissal without new children. `test/transcript-scroll.test.ts` covers interrupted/suspended follow override, layout growth, viewport-fit responses and reader cancellation.
- macOS backend tests: foreground Banner/List options and registered foreground/click delegate selectors, diagnostic summary mappings for center-only/temporary/provisional policies and handler counts, authorization status policy, NSError propagation, duplicate callback behavior and timeout handling. Never initialize the actual center, request authorization or send an OS notification.

Tests must never emit real OS notifications or launch user Pi. Offline demo is an automated fixture, not an app launcher; native tests require explicit user authorization. Run `mise run check`; source/unit evidence is not native acceptance. Build/package the app only on explicit user request, then publish to main's CLI-visible app location per [build workflow](build-cache.md#explicit-build-and-publication-workflow). Native macOS click acceptance and Linux compilation/delivery/action/focus acceptance remain pending; Windows click routing, reopening closed targets, banner withdrawal/grouping, badges, notification history, per-event controls, and rate limiting remain deferred.
