# Notifications: implementation reference

Read the [human guide](../../../../docs/notifications.md) and [architecture](../../../../docs/architecture.md). Paths below are repository-root relative.

## Code map

- `src/pi/session.ts`: Pi-specific attention callback (`completed`, `input`, `failed`), live-run/outcome/latest-finalized-assistant-text tracking, input-dialog queue, disconnect deduplication.
- `src/main.ts`: captures originating tab/token; lifecycle eligibility; notification-safe explicit name; Settings toggle; completion unread marker.
- `src/notifications.ts`: testable policy; initial native focus filter, optional permission preparation, final focus/lifecycle/preference/selection revalidation, latest-attempt status; bounded Markdown-to-plain-text response previews using marked/DOMPurify with all but line-break tags stripped.
- `src/preferences.ts`, `src-tauri/src/preferences.rs`: validated boolean `notifications.enabled`, default true, existing JSONC/CAS writer and cross-window synchronization.
- `index.html`: Settings → Notifications, On/Off selector, Send test notification and Refresh notification diagnostics buttons plus last-attempt/native-policy status. Errors also use the existing project error area.
- `src-tauri/src/notifications.rs`: narrow native command; project-window registry authorization, native settings/exit/focus checks, bounded labels, completion preview validation/truncation and generic input/failure bodies.
- `src-tauri/src/macos_notifications.rs`: macOS-only UserNotifications backend, real bundle validation, main-thread operations, retained foreground delegate, authorization handling and awaited submission callbacks (errors identify authorization versus submission).
- `src-tauri/tauri.conf.json`, `mise.toml`, `scripts/verify-macos-bundle.ts`: whole-bundle local macOS ad-hoc signing and post-build signature/identity/Info.plist/resource verification. Pure signature fixtures live in `test/bundle-signature.test.ts`.
- `src-tauri/src/main.rs`, `src-tauri/Cargo.toml`: app-owned prepare/send/test/diagnostics commands and startup delegate installation; macOS objc2 UserNotifications/Foundation/block2 dependencies. Linux/Windows retain the Rust Tauri notification plugin; no JS notification plugin dependency/capability grant.

## Invariants

- Pi owns semantic lifecycle. Only a live `agent_start` followed by idle `agent_settled` generates completion; no history, `agent_end`, tool result, ordinary snapshot, compaction-only operation or duplicate settled alert.
- Latest assistant `message_end.stopReason` determines failed/completed at settlement; errors during retries do not notify prematurely. Aborted runs and explicit Stop suppress completion. Tool errors alone do not imply session failure.
- `process_error` generates failure once per coordinator; disconnect flag rejects subsequent old events. Shell suppresses intentional close/restart/unload and native exit state suppresses quit dispatch.
- Input attention occurs when an actual supported extension dialog enters the serialized dialog queue, not when an ordinary extension `notify` arrives or a local model/name picker opens. Notification does not alter existing dialog/focus behavior.
- Capture tab/token; never target whatever session becomes active after an await. Recheck validity, preference and selection after native `isFocused`, and repeat after `prepare_notifications` (an OS authorization prompt can remain open). Recheck project registration off the main thread, then selected/native focus, window presence and preferences on the actual native dispatch thread. Old tokens, closing/restarting tabs and unloading windows cannot dispatch late alerts. No replay or retry.
- Background includes another session in the same focused window, another project window, an unfocused selected session, Settings covering the selected conversation, or the remembered session hidden by Needs attention. Shell selection/unread policy uses the presented conversation, not the remembered navigation target. The owning project window's native focus matters, not app-wide activity or webview visibility alone.
- Never use `tab.title` in banners: fallback sidebar titles contain prompt excerpts. Explicit Pi `sessionName` or generic “Session” only. Native project name derives from the calling window's canonical registered directory, not frontend input. Completion body may contain the latest finalized assistant response, including paths/content the assistant authored; never use user-message, thinking or tool-result records. Input/failure bodies remain generic, without dialog title or raw errors.
- Banner title is `project · session`, without a redundant Nimrod prefix; OS chrome/icon supplies application identity. Native labels remove control/bidi formatting characters and cap at 100 Unicode characters. No custom sound/actions. The explicit Settings test is the only intentional focused-session-policy bypass; it uses fixed text and still honors native project/exit/preferences guards. IPC does not start/select/resume/stop processes or acknowledge prompts.
- Settings save failures keep last committed policy, report alongside the control, and restore the picker. Invalid external edits retain last valid settings. Default on is independent of OS permission; no claim of granted/delivered status.

## Response preview pipeline

`SessionUi.attention(kind, response?)` supplies response text only for completed runs. Each `agent_start` clears it; each assistant `message_end` replaces it with string content or joined `type: text` blocks, limited to 16,384 UTF-16 units. An empty latest assistant message yields no preview rather than stale earlier narration. Streaming deltas/history/user/tool messages do not set it. Failed/aborted runs never disclose it.

The shell captures the originating response alongside its tab/token. `notificationPreview(window)` renders the bounded source through marked, strips tags/attributes with DOMPurify (only inert line breaks retained temporarily), extracts text, removes controls/bidi formatting, compacts whitespace and bounds at 1,000 Unicode characters. Longer previews use 999 characters plus an ellipsis. No media, live HTML or link destination is inserted into the app. Conversion failure falls back to the generic body rather than disrupting Pi event delivery/acknowledgements. The normal native dispatch receives optional `preview`; no new model/session query or persistence is added. The OS chooses actual visible line/character capacity; never promise a universal banner size.

Native `body(kind, preview)` accepts previews for completed alerts only, independently normalizes/sanitizes/bounds at 1,000 Unicode characters, and falls back to “Agent finished.” if empty. Input/failure previews are ignored even if passed over IPC. Linux body text is markup-escaped because desktop services may interpret notification markup; macOS/Windows receive literal plain text. OS Notification Center/lock-screen retention may contain assistant text under existing OS policy. No separate preview preference is implemented; the existing On/Off toggle controls all alerts.

## Storage and platforms

`notifications.enabled` is an optional flat boolean in user JSONC settings. No new app-state keys, migrations, Pi writes or project overrides. Omission defaults true on both sides. Uses existing revision ordering, atomic writes and external-edit polling.

Platform direction remains macOS first, Linux next, Windows possible later. macOS now uses Apple's UserNotifications framework directly. Linux/Windows retain Tauri's notify-rust backend: the pinned 2.4 implementation asynchronously ignores downstream delivery errors and desktop permission state is not a reliable reflection of OS authorization. No click-to-session routing is implemented on any platform. Do not wire mobile `onAction` APIs and claim desktop routing.

### macOS backend replacement and diagnostics

Historical acceptance: the user initially observed Notification Center entries without foreground banners. An additive legacy `shouldPresentNotification:` hook was attempted, but subsequent user acceptance still produced neither banners nor Notification Center entries with both application and macOS notification settings enabled. Do not treat the earlier mocked/runtime tests as delivery acceptance or conclude the actual missing-delivery cause is established. One concrete backend defect was found: Tauri's `show()` returns Ok after spawning dispatch, ignores `notification.show()` errors, and also ignores macOS `set_application()` errors.

The legacy hook file is removed. macOS session alerts now bypass that plugin path entirely, using `UNUserNotificationCenter` without NSBundle swizzling or Terminal/Finder identity borrowing. The plugin remains registered for other platforms but is not called by the macOS prepare/send/test path. `center(identifier)` verifies the actual main bundle matches Tauri's identifier before accessing the singleton (unbundled calls can raise Objective-C exceptions). All center operations are scheduled through Tauri's main thread. A main-thread `OnceCell<Retained<NotificationDelegate>>` keeps the weak delegate alive; unexpected existing delegates fail rather than losing somebody else's callbacks.

`notifications::initialize` now runs during Tauri setup, before window creation, rather than first attaching the delegate during a late test/run completion. Packaged matching-bundle processes call `center()` and retain the delegate then; unbundled dev executables skip this initialization and still report the packaged-app requirement on an attempted send. Integration initialization errors are nonfatal to app startup and are rechecked/reported by subsequent commands. Startup does not request authorization or post anything. Moving registration earlier follows [Apple's explicit pre-launch delegate requirement](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate); do not claim it fixes foreground delivery without native evidence. Source ordering was checked in the pinned Tao/Tauri stack: macOS `applicationDidFinishLaunching` calls `AppState::launched`, which synchronously dispatches NewEvents(Init); Tauri runs its setup on runtime Ready. Keep initialization in that startup path, not a queued frontend command.

The stateless objc2 delegate implements `userNotificationCenter:willPresentNotification:withCompletionHandler:` and calls its completion exactly once with Banner | List, never Sound/Badge. No custom actions/userInfo/navigation are added. System styles, Focus and lock-screen policy remain authoritative.

`prepare_notifications` authorizes only registered project windows. macOS preparations are serialized by an async mutex: read actual UN authorization settings; request Alert authorization only if NotDetermined; reject Denied/unknown states explicitly. First-time permission handling precedes the shell's final focus/selection/lifecycle revalidation, so a long permission prompt cannot dispatch a retired/read originating session. Authorized preparations do not re-prompt. The command performs no Pi operation.

`notify_session` returns `submitted` or `suppressed`; the native macOS send validates immutable window/project ownership off-main (the router holds its registry while awaiting main-thread window creation), then rechecks exit/preferences/window/focus on the actual dispatch thread, builds a UUID-identified immediate request, and awaits `addNotificationRequest`'s completion/error callback. Only owned strings/primitives cross callback/async boundaries. Completion-channel state tolerates duplicate/late callbacks. Settings/submission waits time out after 10 seconds, authorization after 120 seconds; no automatic retry/replay. A queued main-thread task does not start if its receiver already timed out. Already-submitted timeout is ambiguous, not proof that the OS rejected it.

`notification_diagnostics` is project-window authorized and read-only: no permission request, dispatch, session access or preferences write. macOS reads actual UN authorization/alertStyle/alertSetting/notificationCenterSetting plus `NSApplication.isActive()` on the main thread, then formats only owned metadata. `FOREGROUND_CALLS` is a process-local atomic counter incremented exclusively in the actual `willPresentNotification` callback before the immediate Banner | List completion. Counts aggregate all project windows and reset with the process; a snapshot's zero is not proof a future/pending callback cannot occur. Refresh after accepted delivery, rather than inferring a per-request receipt from this counter. Non-macOS returns an explicit diagnostics-unavailable description, not guessed policy.

The shell automatically reads diagnostics after an accepted manual test, and exposes a separate refresh button even while alerts are Off. Reads/test actions are serialized through their disabled controls; diagnostic failure appends to the already-accepted test status, never relabels it a delivery failure or marks a Pi session failed. A manual refresh itself never runs prepare/send or starts/stops a child. No timers/polling, persisted counters, live response content, OS notification-setting changes or focus/navigation are introduced.

The Settings test uses the same authorization/dispatch path with fixed `project · Notification test` title and fixed body, passing selected=false by explicit user action. It does not start an agent, make a model request, inspect a session, or change notification preferences; Off disables the button and native guards still apply. Latest session status distinguishes quiet reasons, preparation, submitting, accepted submission, native suppression and errors. macOS errors are copied into both Settings and the existing project error area; no session failure or Pi acknowledgement is inferred.

#### macOS 27 investigation

Read-only `sw_vers` confirms macOS 27.0.1 (26A434). Apple's [macOS 27 release notes](https://developer.apple.com/documentation/macos-release-notes/macos-27-release-notes) list a Notification Center dismissal fix, not a foreground-banner policy change; no UserNotifications-specific replacement policy was found. The installed macOS SDK still exposes the same `willPresentNotification` selector and Banner/List options (available since macOS 11). [Apple's current delegate docs](https://developer.apple.com/documentation/usernotifications/unusernotificationcenterdelegate) explicitly require installing the delegate before launch finishes and warn late installation can miss notifications. The running earlier signed build installed on first notification; the staged diagnostic build moves this to startup. This is a concrete lifecycle suspect, not proof of a macOS 27 regression or a verified foreground fix. Use actual callback counts/API policy from the new process before attributing suppression to the OS. Existing tests/registration timings are not evidence the new code took effect without restart.

Native follow-up on the diagnostic build: the immediate post-submit snapshot showed 0 calls, but an explicit later refresh showed 2; this was callback timing, not evidence of a missing delegate. Passive logs for the test show successful entitlement checks, DND `interruptionSuppression: none` / `resolutionReason: disabled`, `Presentation reply dev.nimrod.desktop ["list", "banner"]`, and usernoted `Presenting ... as banner`. NotificationCenter then queues `present` and stores the record, with no desktop banner observed by the user. Thus the OS actually receives the requested flags; do not blame delegate registration or block ABI solely from the initial zero. A separate inert Swift `UNMutableNotificationContent()` probe on this Mac reports interruption level 1, matching Active; it never initializes a notification center, requests permission or posts anything. The remaining fault is unverified desktop presentation/policy after the banner decision; no macOS 27 rule change or UI regression is yet established. `canDisplayWhileCenterIsClosed: false` appears on the stored list-item log, but its private semantics alone are not proof of a causal blocker. The user then performed the Persistent-versus-Temporary A/B test: changing only style to Persistent made foreground test alerts visible. This establishes a working signed/native foreground path under Persistent and narrows the remaining inconsistency to Temporary presentation or its cached policy on this macOS 27.0.1 setup. It does not establish an intentional OS rule change, every Mac being affected, or that native registration alone caused the earlier failure. No production flag/priority workaround, time-sensitive/critical entitlement, sound, permission reset or automatic OS-style override was applied. Keep native style user-controlled and document Persistent as the currently user-accepted workaround; switching back to Temporary is an optional cache-versus-reproducibility check, not a prerequisite for using working alerts.

#### Whole-bundle signing correction

The user's explicit Settings test returned `UNErrorDomain / 1` (Apple's `UNErrorCodeNotificationsNotAllowed`). Inspection of the previous packaged app showed `Identifier=nimrod-<linker hash>` instead of `dev.nimrod.desktop`, `flags=... (adhoc,linker-signed)`, `Info.plist=not bound`, no sealed resources and failed `codesign --verify --strict`. This is not a valid signed application bundle. UserNotifications requires application signing; a macOS settings entry does not establish that a newly built executable's code identity is allowed. [Electron's migration note](https://electronjs.org/blog/electron-42-0) independently documents the same UserNotifications signing requirement.

The configuration now sets `bundle.macOS.signingIdentity` to `-` for whole-bundle local ad-hoc signing. `mise run build` runs `npm run verify:bundle` after Tauri packaging: verify strict code validity, reject linker-signed flags, require signing identifier to match configured bundle identifier, and require bound Info.plist/sealed resources. It uses `CARGO_TARGET_DIR` when present, or an explicit app argument, and skips the macOS check on other host platforms. It only reads the artifact; no launch/notification/permission mutation occurs. Test fixtures exercise full ad-hoc/certificate signatures versus wrong identity, linker-only and unsealed metadata.

No certificate is created/imported and no Keychain/TCC/OS notification settings are changed. This is local ad-hoc signing, not Developer ID/notarization, and its implicit designated requirement can change with a rebuild; do not promise grants survive rebuilds. A stable certificate is a separate, user-authorized future step. Never repair a running user's bundle in place: stage a separate artifact for signing/acceptance. Corrected native errors now identify the failing authorization/submission phase. The user subsequently confirmed that the signed build's explicit test notifications reach Notification Center without errors, but desktop banners still do not appear. Passive native logs show two accepted requests with hasError=0; existing logs do not establish whether our foreground delegate ran or reveal alertStyle/Focus policy. The SDK confirms Banner | List support on macOS 11+ and the implemented selector signature. The user then explicitly confirmed Temporary style, Desktop/Notification Center/Lock Screen checked and Focus off. One subsequent completion displayed a banner without restarting (therefore not caused by the unlaunched diagnostics/startup edits), followed by another foreground completion that reached Notification Center without a banner; the foreground failure remains unresolved/intermittent. Startup installation and read-only API/callback diagnostics were added to distinguish platform policy from an uncalled handler rather than repeat permission resets. Do not treat enabled delivery/Notification Center as proof of enabled banners. Signature verification by itself remains distinct from delivery acceptance.

Follow-up passive native logs showed the signed artifact opened, ran for roughly 22 seconds with its own WebKit processes, then exited; the default artifact opened afterward and its process produced the later authorization failure. The reported unphased `macOS notifications:` error also belongs to the older binary, whereas the staged signed build reports `macOS notification authorization:` / `submission:`. Do not attribute this sequence to single-instance forwarding without evidence, or treat it as a delivery test of the signed build. The shared project error area persists across session selection and does not imply every Pi session failed. The normal launcher still targets the default artifact; wait for explicit user quit/approval before publishing the verified copy there, never patch a running bundle in place.

Unbundled development executables now report an explicit packaged-app requirement instead of using Terminal's identity. Packaged macOS native acceptance remains user-owned; compilation and mocked commands do not establish receipt. Linux needs a desktop service; Windows needs installed application identity. No platform parity, permissions, DND, sound or activation acceptance is established by unit tests/build. Root-directory projects use a generic Project label when no final path component exists.

## Tests and verification

- `test/session.test.ts`: intermediate/duplicate settled suppression, aborted runs, final errors and successful retries, extension input versus ordinary notices, disconnect deduplication, existing acknowledgement/queue semantics, latest-finalized-response extraction, run resets and failure exclusions.
- `test/notifications.test.ts`: foreground/background focus policy, disabled/retired targets, selection/focus/lifecycle/settings changes during authorization, authorization failures/native suppression status, nonfatal errors, plain-text Markdown conversion, unsafe HTML/media stripping and Unicode-safe preview bounds.
- `test/shell.test.ts`: actual shell with mocked native boundary; background/selected/unfocused routing, generic labels despite private prompt titles, completion previews without reasoning, intentional-close suppression, persisted/off/external settings and input-dialog alerts without process interruption; explicit All/Working → Completed dispatch status; manual test/off policy with no process commands, read-only refresh while Off, metadata display, nonfatal diagnostics lookup failure and native errors in Settings/project error surfaces.
- `test/preferences.test.ts`: default, JSONC preservation, boolean validation, last-valid retention.
- Rust notification tests: bounded/sanitized labels, completion preview normalization/truncation/fallback, generic input/failure bodies and enum validation; native preferences tests validate boolean settings.
- `test/browser/workspace-tabs.spec.ts`: offline All/Working → Completed captures preparation/send/status, and Settings test/off/read-only-refresh policy never starts/stops extra agents or emits another notification. Both native notification commands are mocked, never delivered.
- macOS backend tests: foreground Banner/List options and registered delegate selector, diagnostic summary mappings for center-only/temporary/provisional policies and handler counts, authorization status policy, NSError propagation, duplicate callback behavior and timeout handling. Never initialize the actual center, request authorization or send an OS notification.

Tests must never emit real OS notifications or launch user Pi. Use offline demo for user-directed native acceptance. Run `mise run check` and `mise run build`; source/unit evidence is not native acceptance. Click routing, banner withdrawal/grouping, badges, notification history, per-event controls, and rate limiting remain deferred.
