# Session creation and default harness

**Status: source implemented; new fixtures authored, unrun.** [Sessions](../../../../docs/sessions.md#create-a-session) owns user guidance; [preferences](preferences.md) owns JSONC layering/storage, [command interactions](command-interactions.md) owns palette dismissal/focus, and [durability](session-durability.md) owns saved versus temporary semantics.

## Contract

- `sessions.defaultHarness` defaults to `pi`, with global and canonical-project overrides. Project Settings → Interaction shows the effective value, provenance and Remove override. Removing the project key resumes inheritance, including equal-valued explicit overrides. No startup write or migration. Harness IDs use lowercase letters/digits/hyphens, begin with a letter and have at most 64 characters; well-formed unavailable/unregistered IDs remain stored rather than being silently rewritten.
- New session (`new`), New named session… (`new-named`) and New temporary session (`temporary`) use the effective preference at intent. Existing default shortcuts stay unchanged. Selected/last-used sessions never determine it. Resume, Reload, restored membership and existing sessions are unaffected.
- New session with harness… (`new-with-harness`) and New temporary session with harness… (`temporary-with-harness`) always offer an explicit choice, preselecting the effective default when eligible. Both are bindable, initially unbound. New named session… always offers its harness list and retains `primary+alt+n`; the separate `new-named-with-harness` action is removed. One-off choices never change settings. Old `new-copilot`/`new-codex` and separate named-picker overrides remain inert unknown IDs and untouched.
- `HarnessCreation.modes` and `.named` remain required adapter declarations on registrations/projects. Creation action metadata no longer belongs to adapters: the shell owns the five actions, while adapters own capabilities, launch and native naming semantics. The registry rejects unsupported requests before adapter construction. Named creation requires both saved mode and initial naming; rename support alone is insufficient. Temporary support must mean genuinely unsaved history, not saved-then-delete emulation.
- Discovery intersects type capabilities with the project's once-per-startup executable availability and independent initialization readiness. Do not start a conversation or probe a model to populate choices. Only Pi currently advertises temporary and initially named creation; Copilot/Codex advertise saved creation only. Generic ACP remains outside product composition.
- If the configured default is unavailable, unregistered, not ready or lacks the requested capability, ordinary creation opens the corresponding explicit picker with explanatory guidance. Never silently substitute, rewrite the setting, emulate capabilities or change creation type. Actions with no eligible harness are absent/disabled; a picker already entered with no choices cannot create anything.
- Named creation always shows one palette modal with a name field and inline Harness listbox, plus Create/Cancel. Name receives initial focus. Select the effective default when eligible, otherwise the first eligible harness with the existing default-fallback explanation; never remember last-used selection. Unmodified Up/Down from the name field or focused list wraps harness selection without moving focus or changing the name/caret. Repeated arrows may navigate; modified arrows and composing/keyCode-229 keys remain untouched. Typing only updates name validity: it never filters/rebuilds the harness list or resets selection. Tab can focus the list; its `aria-activedescendant`/row `aria-selected` track selection and the shared live status identifies the selected harness for name-field navigation. Pointer clicks select only, without creating. Enter from Name/list or Create submits once, excluding IME/repeated Enter; Escape/native cancel/Cancel creates nothing. Empty/whitespace names or no eligible harness disables Create. Footer arrows retain shared dialog navigation; Left/Right in the Name field stays native. There is no nested harness modal and no launch before acceptance.
- Normal/temporary harness selection reuses `startSelection`; naming reuses `namedSession`. Both retain shared modal-motion, dismissal invalidation and close-time focus restoration. Capability/availability readiness is rechecked at launch. Captured intent is not retargeted by later preference broadcasts. Once selected, session creation activates its local row immediately and connects through the existing lifecycle; no prompt, automatic retry or replay is added.
- The registry's `primaryId` is the composition's native bootstrap/legacy last-session owner, not the user-editable creation default. Do not use it to route new conversations.

## Code and fixtures

- `src/session-creation.ts`: preference validation and identity-independent capability/availability/default resolution.
- `src/main.ts`: shared action/button/shortcut creation routing and launch revalidation; ordinary command details identify the effective harness.
- `src/command-palette.ts`: combined named form and selection guidance; mounted fields retain their local values.
- `src/settings-surface.ts`, `settings-choice-controls.ts`: registered harness choices in both Settings scopes without runtime probing; normal provenance/reset and JSONC error routing.
- `src/preferences.ts`, `src-tauri/src/preferences.rs`, `project_preferences.rs`: mirrored validation and project allowlisting.
- `test/session-creation.test.ts`, preference/native fixtures, combined-form palette tests, Settings-choice tests and shell creation/default/fallback tests cover discovery without hardcoded harness IDs, equal overrides, last-valid values, cancellation/IME/repeats, name preservation, one-off defaults and unchanged mounted sessions/drafts. Existing harness creation fixtures now enter through the shared picker. Browser fixtures follow the same explicit selection path.

These new/updated fixtures have not been executed for this task. Only the required post-merge compile check is automatic; it is not native acceptance. macOS/Linux modal appearance, inline-list/keyboard/focus and installed-runtime creation remain user validation work. No build, app launch, paid model request or upstream harness change was performed.
