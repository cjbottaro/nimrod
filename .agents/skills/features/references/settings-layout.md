# Settings layout and category navigation

**Status: implemented.** This reference owns current specifications and implementation details. [Verification status](verification.md) separates fixture evidence from native acceptance; [historical records](history/feature-records.md#settings-layout) retain prior execution records.

## Specification and acceptance criteria

Global Settings is one app-owned native window (`settings`), reused/focused on repeated opens and available without a project. It has an independent frontend bootstrap with no session controllers, plugin loading, drafts, harness calls or project teardown. Closing it uses the ordinary native close path, not project shutdown/geometry persistence. A newly created Settings window is hidden/unfocused until the frontend has mounted the page and applied its initial theme, translucency, native title tint/material and zoom. Repeated opens while loading queue/reuse that same window without exposing its blank webview; already-ready opens focus it immediately. Project settings remains a full-window modal page in the owning project window, preserving the underlying conversation. Both share the same mounted controls/category layout and app-wide sidebar width.

Global Settings exposes Appearance, Notifications, Diagnostics, Keybindings and Runtime; Project settings exposes Appearance (theme only) and Runtime only. Translucency, zoom and auto-follow controls are wrapped in `#settings-translucency` / `#settings-zoom` / `#settings-send-auto-follow` and hidden as complete groups in Project settings, with no source/reset rows for these global-only settings. Their shared controllers remain installed for global synchronization, native appearance/zoom and subsequent-submit configuration; keyboard zoom edits the global value. Global-only categories are hidden and excluded from category keyboard navigation. Global Settings links to open projects with explicit overrides; links focus the owned project and use a native queued request consumed after frontend boot. The Project bar uses the classic Lucide `settings` icon from 0.468.0 (unaltered SVG geometry, existing 18px size/1.7 stroke, round caps/joins; license/provenance in `THIRD_PARTY_NOTICES.md`), not a custom gear drawing. It opens Project settings (or global Settings from the welcome window). `settings` / `primary+,` opens/focuses global Settings; `project-settings` / `primary+shift+,` opens the active project's page; `keybindings` has no default and opens global Settings directly at its Keybindings pane. Explicit stored bindings are untouched.

Each project control shows its effective value and source (`Global default` / `Project override`). `Use global default` deletes the project key. The header names the project and offers `Open global settings`. The header remains 48 CSS pixels high to preserve application-notice-strip placement; long identity/scope text ellipsizes rather than changing that contract. [Preferences](preferences.md#project-layering) owns merge, provenance and storage semantics.

Settings categories remain mounted with independent reading/dirty-control state. Its app-wide sidebar width is independent of project widths; browser modality and resize guards preserve the underlying conversation and nested-dialog focus.

## First native presentation

Cold Settings creation uses `.visible(false)` / `.focused(false)` and an ephemeral UUID `settingsGeneration` in its entry URL. After the page/category is mounted, `surface.settled()` waits for current initial appearance and zoom work; `window-presentation.ts::presentWhenPrepared` owns layout flush, once-only reveal and unload cancellation before `settings_window_ready`. Do not wait for hidden-webview rAF or arbitrary timers: they can be throttled. Runtime PATH/mise discovery starts **after** reveal and leaves only its fields disabled while pending; it must not gate the window's first appearance.

The native ready command accepts only its Settings caller and current creation generation, and consumes readiness once through the shared native `PreparationGate` (generation/readiness under one mutex). Old/closed-window signals cannot show a replacement; repeat signals do not refocus. Native Close/unload/Quit suppress late frontend reveal. Generic app/CLI focus routing excludes unready Settings, so it cannot bypass this boundary. Normal startup/appearance failures report through the existing application notice strip and reveal the prepared error/fallback window rather than silently retaining a hidden singleton. A failed native presentation is not automatically replayed; another explicit open can focus a ready window.

This is a narrow initial-window **presentation-readiness exception** to optimistic interaction: showing a partially initialized opaque/blank webview would violate the first-display contract. It is not a general RPC gate for Settings edits, themes, zoom, session navigation or Send. Project settings remains immediate in its already-mounted project window. No harness call, draft mutation, process restart or conversation reconstruction.

## Code map

- `src/global-settings.ts`, `src/native-preferences.ts`, `src-tauri/src/settings_window.rs`: independent global boot, scoped snapshot adapter, concrete native singleton/category authorization and queued project-link requests. `src/window-presentation.ts` owns first reveal and resources registered as they are acquired, including partial/late boot cleanup. `src-tauri/src/window_presentation.rs` owns composition/focus and the prepared generation gate; generic focus still excludes unready Settings. See [boundary map](window-presentation.md).
- `index.html`: full-viewport native `#settings-page` dialog; fixed `.settings-header` above `#settings-layout`. Category sidebar buttons are vertical ARIA tabs controlling mounted `.settings-panel` tabpanels. Appearance initially shown; Notifications/Diagnostics/Runtime initially hidden. Keybindings is inserted before Runtime by `src/keybinding-editor.ts` before navigation initializes.
- `src/workspace.css`: shared `.sidebar-layout`, `.layout-sidebar`, `.layout-content` and `.sidebar-resizer` primitives used by both Settings and the project. Each layout aliases its own width variable into `--sidebar-width`. Session-only overlays, filters, recency and activity styles stay separate.
- `src/theme.css`: category selection/hover styling, full-width panel overflow and 20px interior side/top gutters (32px bottom). The content wrapper does not scroll: each panel independently owns overflow. Do not center/cap the scroll owner or put its gutter outside it. Global preference errors remain above the selected panel; file paths live under Runtime.
- `src/settings-navigation.ts`: category selection, vertical Up/Down wrapping, Home/End, roving tabindex and hidden-panel projection. It guards closed pages and nested dialog ownership, and never recreates controls. Selection survives reopening Project settings within that project window; global Settings retains it while its native window remains open. It is not persisted or synchronized.
- `src/sidebar-resize.ts`: same controller for both sidebars; optional width property, bounds/default, available-width cap, active predicate and allowed owner dialog. Defaults preserve existing Session sidebar behavior. Native dialog `open` changes trigger immediate drag cancellation/visibility refresh. Escape cancels a drag without propagating to close the owner page.
- `src/settings-surface.ts`: installs shared controls and navigation (after the Keybindings editor in global Settings); Open keybindings explicitly selects its panel before focusing search. Separate Settings width callbacks read/write through `preferences`, not the project's `localState` cache. Subscription reloads only when the width key changes, avoiding cancellation on unrelated updates. Existing `src/settings.ts` retains page modality/Back/Escape and Runtime Save semantics.

[Translucency](translucency.md) owns alpha surfaces and the conditional visibility of the underlying workspace while translucent Settings is open; it preserves modal layout, mounted nodes and scroll geometry.

## State and sizing

`nimrod.settings.sidebar.width` in app-managed state is independent of `nimrod.sidebar.width:<canonical cwd>`. Valid Settings preferences are rounded/clamped to 160–360 CSS pixels; default 220. Double-click saves null/default. Its rendered maximum is the lesser of 360, 45% of layout width, and layout width minus 240px (bounded at zero). The minimum decreases when the viewport cap requires it. Narrow Settings stays split rather than inheriting the Session sidebar's overlay/collapse policy; category labels ellipsize if necessary. Window/zoom clamping does not rewrite the preferred value.

Successful release saves once; keyboard/reset saves immediately via the existing native app-state writer and error surface. Width restores across projects/restarts and receives revision-ordered broadcasts into already-mounted windows, even with Settings closed. A width broadcast cancels an in-progress drag, preferring the authoritative saved value. No category selection, search, scroll offset or Runtime dirty value is saved as part of resizing. Persistence failures surface locally and do not guarantee durability.

## Invariants

- Category hover styles apply only to unselected tabs (`:hover:not([aria-selected=true])`); hover must never override the selected background/foreground. `test/browser/settings-hover.spec.ts` checks selected hover stability and unselected hover feedback before and after switching categories.
- Keep all exposed panels mounted. Category switches preserve unsaved Runtime fields, Keybindings queries and per-panel offsets; reopen preserves the last category in that window. Restart loses transient navigation/editing state.
- Session and Settings widths are independent. Never share session membership, recency/filter controllers, project-local caches or native process semantics merely to share layout.
- Allow resize interaction within Settings only while that exact owner dialog is open. Nested Pi/Keybindings dialogs block navigation/resizing; opening one, closing Settings, blur or viewport changes cancel an unfinished drag without saving. Closed/hidden handles cannot mutate state.
- Keep browser modality, nested-dialog priority, prior-focus restoration and underlying project geometry. No transcript/controller replacement, harness IPC, prompts, session teardown or draft mutation from category selection/resizing.

## Tests and acceptance

Scoped Settings regressions are authored but not executed for this change: `test/preferences.test.ts`, `test/settings.test.ts`, `test/shell.test.ts`, native project-preferences fixtures, and `test/browser/settings-scopes.spec.ts`. Existing browser Settings/layout/keybinding/notification fixtures now model the independent global window. No tests, checks, builds or native acceptance have been run for the scoped implementation unless separately requested. Native singleton/menu shortcuts, window focus/close, file editing, project links and cross-window overrides need macOS acceptance; Linux remains unverified.

- `test/window-presentation.test.ts`: prepared layout/reveal once, native-failure no replay, error fallback, unload cancellation, reverse owned cleanup and late resource disposal; authored, not run for the refactor.
- `test/settings-navigation.test.ts`: vertical tab wrapping, mounted dirty controls/offsets, owner/nested modality and disposal.
- Rust presentation-gate/Settings fixtures: generation/idempotent ready consumption, stale-window rejection and hidden/unfocused construction guards; source fixtures are not native first-frame acceptance.
- `test/shell.test.ts`: cold ready ordering with delayed appearance/title tint, initial zoom, non-gating runtime discovery, readable startup errors and close-before-ready suppression; app-wide width restore/save/broadcast across two project windows, independent project widths/categories and no harness/settings operations.
- `test/browser/settings-layout.spec.ts`: offline WebKit wide/default/narrow split bounds, no horizontal overflow, gutter-inclusive panel scrolling, fixed sidebar/header, retained edits/search/reading/category, keyboard tabs, zoom-aware dragging, preferred-width clamp/restore, keyboard/default reset, drag Escape versus page Escape, nested recorder guard and restoration in another window fixture.
- Existing sidebar resize unit/browser regressions preserve session behavior, zoom, focus/drafts, live follow and older-history pause. `test/browser/settings-sync.spec.ts` keeps dirty Runtime/background rendering coverage; browser Keybindings/notification tests now explicitly select their categories.
- `scripts/check-settings.mjs` includes shared layout CSS and navigation, and explicitly selects categories for its isolated Chromium modality/geometry check.

Run `mise run check` and `npm run test:browser`. Build/package the app only on explicit user request, then publish to main's CLI-visible app location per [build workflow](build-cache.md#explicit-build-and-publication-workflow). Fixtures do not launch the user's app, call models, read real sessions or post native notifications. Passing WebKit/DOM tests are not native Tauri acceptance; ask the user to validate visual density, zoom/pointer resize and two-window synchronization in the packaged macOS app. Linux/WebKitGTK and possible future Windows/WebView2 remain unverified.
